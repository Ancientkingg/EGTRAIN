# Custom dialog presentation contract

Use `widgets/DialogLayout.h` for new or migrated custom `QDialog` forms. Supply the name of the dialog as the heading and a short context once, and place fields, units, help, and inline status inside the body widget. Show help text with `DialogLayout::setHelp(label, text)` and inline status with `DialogLayout::setStatus(label, severity, text)`, where `DialogLayout::Severity` is `Neutral`, `Warning` or `Error`. Both show the text as plain wrapped text in a label that has a parent widget (the dialog body or an editor panel), and an empty text hides the label. A label has either the help role or one status role, and a call can change it also after the dialog is shown. The helpers set the `dialogHelp` and `dialogStatus` properties that the stylesheet selects on. Neutral empty and successful states are not warnings. Keep labels associated with their fields and retain keyboard tab order.

`DialogLayout::install(dialog, heading, context, body, buttons)` transfers the body and button box to the dialog. It makes the heading the window title and does not repeat it inside the dialog, so the name shows once, in the title bar, and the body starts with the context line. It gives the context and body a resizable scroll viewport while keeping the button box outside it. The combo boxes and spin boxes in the body change with the mouse wheel only while they have keyboard focus (`widgets/FocusWheel.h`), so the wheel over a field scrolls the body; `ChoiceComboBox` and `CompactDoubleSpinBox` do the same wherever they are used, and the editor docks guard their fields from where the main window gives each dock its scroll area, which also covers fields that appear later. The footer buttons are styled again after the body is installed, because a caller names them and chooses the default before that, and a style cached by then misses the rules that name them. Keyboard focus entering the body scrolls the focused control into view. The context is forced to plain text so authored names are never interpreted as markup; a window title is always plain text. Its size cap uses the current screen's available geometry (90 percent of the width and 80 percent of the height); the optional rectangle supports deterministic tests. The dialog opens at the height its content needs, so the viewport scrolls only when the content is taller than that cap, and `DialogLayout::fitWidthToContent` makes it taller again after a change to the body. A message that `setStatus` or `setHelp` shows in a shown dialog does the same once the layout has made room for it, and the height counts every visible widget that a caller adds to the dialog layout. Other changes to a shown body do not make the dialog taller unless the caller calls `fitWidthToContent`, as the Run details toggle of the run review does. The body takes any height the dialog has beyond that, and the context line keeps the height of its text. Margins follow the dialog's system font. Supply a `QDialogButtonBox` with task-appropriate roles and let Qt order its buttons for each platform. The helper does not connect buttons, select a default, validate, accept/reject, or mutate a model. It gives the focus to the first field of the body, a widget that Tab reaches other than a push button, a tool button or an item view, and without one to the default button: the button the caller made the default, else the first accept button, which the button box makes the default when the dialog is shown. Otherwise Qt 5 gives the focus to the first button of the footer, Cancel on macOS and in GNOME, and a button takes the default while it has the focus. A caller that wants another first focus sets it after `install`. In a footer laid out for macOS the footer buttons are not auto default, so a footer button that gets the focus leaves the default where it is, as in native dialogs; a push button in the body still takes the default while it has the focus. Elsewhere a footer button with the focus is the default. Space presses the focused button everywhere. The caller must explicitly wire acceptance and rejection, choose a safe default, and preserve its existing transaction/Cancel semantics. Never make a destructive action the Enter default. Use regular `QFileDialog` and `QMessageBox` unchanged rather than applying the custom layout to them.

The stylesheet retains transitional `runReview*` selectors for compatibility. Every `QDialog`, message boxes included, is one surface: the plain widgets, frames, labels, check boxes and scroll areas inside it take the colour of the dialog, so the body shows no box of its own, while fields, lists, tables and status labels keep their own faces. A group box in a dialog is a bold title over its fields, without a frame. The default button of every dialog footer and `QMessageBox` has the same filled face, hover, pressed, focus and disabled looks, so that the Enter default shows in every prompt. The buttons of a footer and of a message box show their text without an icon. `main` applies the stylesheet before it shows the first message box, so a case that cannot be opened at startup is reported in the same look. [Interface style](interface-style.md#dialogs) gives the colours and sizes. The default button differs by colour only and keeps the weight of the other buttons, because Qt sizes a button before a state rule applies and a bolder default text would be wider than its button. The disabled look applies throughout the application: disabled push buttons, combo boxes, line edits and spin boxes have a grey face, a light border and grey text in dialogs and main-window panels. A disabled default button in a dialog footer keeps its lighter grey. A read-only line edit keeps its read-only look when disabled. Disabled tool buttons and check boxes change only their text colour, except the toolbar buttons, the **Open result view...** button of Run Results and the **Trains**, **Occurrences** and **Stations** buttons of the result windows, which have the look of a disabled push button; checked tool buttons keep their checked look. A disabled menu entry has grey text. These rules restyle no other widget.

## Callers

Run review, the case chooser, timetable-stop editing, blocking-time scope and capacity options use this layout. The delay analysis window and capacity analysis results also use it: long run identities and section context wrap as plain text in the scrollable content, tables and secondary CSV/diagram actions remain in the body, and Close stays in the fixed footer. Run review separates its summary from expandable configuration details. The case chooser groups bundled and recent cases and keeps creation/import actions in a secondary menu.

Choice combos whose entries can be long imported names use `widgets/ChoiceComboBox.h` instead of a plain `QComboBox`; the timetable stop editor and the blocking-time scope and capacity options dialogs do. With it, long station or platform names never force a horizontal scroll bar. The field can shrink below its text, while its size hint lets `DialogLayout::fitWidthToContent` widen the dialog to the content within the same width limit as `install`. A selected text that is still wider than its field is drawn with its middle elided. The tooltip is the full current text, and the popup list is as wide as its widest entry within 90 percent of the screen's available width, eliding the middle of entries that still do not fit. Callers set `Qt::ToolTipRole` on an item to explain it, as the timetable stop editor does for an invalid imported platform or a station that is not on the route. The route field of the Services dock is also a `ChoiceComboBox`; its tip adds the stations of the selected route to the text of the field.

The stop table of the Timetable tab (`TimetableStopsPanel::fitColumns`) needs no horizontal scroll bar down to the minimum width of its columns. The platform, dwell and planned time columns take the width of their header or of a value of up to ten digits, whichever is larger, using the font metrics of the table. The station column takes the rest, at least six digits, and its whole header where the other columns can give up that room. In a table too narrow for that, the four narrow columns shrink in proportion. Cell text that does not fit is elided, and the tooltip of a cell holds the full text.

The reference-route chooser for the timetable graph and train paths is a list dialog (`diagrams/RouteReferenceChoice.h`): all choices are visible at once, rows wrap, and a double click or Enter accepts the selected row.

Composition membership uses the standard single-choice `QInputDialog`. File selection, warnings and confirmations retain `QFileDialog` and `QMessageBox`.

`test_dialog_presentation_contract` checks the case chooser and the Run simulation dialog in the built application; [Checks](#checks) says what it covers. Widget tests cover bounded dimensions, enlarged fonts, scrolling and keyboard access to the fixed footer, and the look of disabled controls inside and outside dialogs.

`test_dialog_presentation_contract` checks the case chooser and the Run simulation dialog in the built application on the offscreen platform. It runs `tools/e2e/creator_acceptance_smoke.sh --dialog-contract`. The script starts the creator acceptance run, which saves a scene, and then starts `tools/e2e/dialog_presentation_contract.py` with the application and that scene. The `scene_tool` validations and the data checks of the default mode of the smoke do not run in this mode. CTest registers the test on macOS and Linux and not on Windows, because the scene comes from a Bash script. The pull request checks run it, and so do the validation and sanitizer jobs of the release workflow. It has the labels integration, gui and slow. The application reaches the checks through the hooks `dialogShown` and `dialogClosed` of `MainWindowTestHooks`, which `showStartupChooser` and `RunController::showRunReview` call around the dialog. `tests/e2e/Dialogs.cpp` answers them, and the release build does not contain it.

To run it by hand, set `QEGTRAIN_APP` and `QEGTRAIN_SCENE_TOOL` to the built programs, then run:

```bash
bash tools/e2e/creator_acceptance_smoke.sh --dialog-contract
```

For the case chooser the script checks that:

- the first row is the group heading Bundled cases and is not enabled;
- the row that is selected when the dialog opens, which is the first enabled row with a case path, is the first bundled case, whose name the script reads from the first folder of `EGTRAIN/QEGTRAIN/Scenes`;
- Open is enabled;
- the left button reads Continue while a case is loaded;
- the loaded case and the scene revision are unchanged.

For the Run simulation dialog the script starts the application for each variant of the saved scene. The variants change which service runs enter during the period (including none), the warnings, the incident configuration, the length of the case and scenario names (including markup characters and an 18 point font) and the signalling area. Each variant runs with advanced details off and on, and the dialog is closed with the Cancel button and with Escape. The script checks:

- the fact values, the details text, the context line, and the status text with its warning flag;
- the validation counts and the incident configuration text, which appear only with advanced details on;
- that Run simulation is the default button and has the first focus;
- that the dialog stays within 90 percent by 80 percent of the available screen with the footer visible in the collapsed, expanded, scrolled and collapsed again states, and that the footer does not move when the body scrolls;
- that Tab moves from the body to the footer and Shift+Tab moves back;
- the state of the details toggle;
- a size limit with the large font;
- that Cancel and Escape start no run and leave the scene unchanged.

The script does not open the other dialogs of the inventory.

## Result windows

`DiagramWindow::setPresentation(heading, context, warning)` supplies a short window heading, optional run/scope context and an optional concise interpretation warning. Diagrams have no expandable technical-detail panels. The warning wraps above the capped, top-aligned context without a fixed height limit, so long identifiers cannot clip it. Callers document calculation details in the user guide. The chart's axes, samples, time formatting and export provider are unchanged. The window never guesses from chart titles: callers set chart/window titles explicitly. Authored IDs may contain `|`, so delimiter-based title parsing is unsafe. `setRollingStockSubject(true)` hides the train filter and train selection controls and uses input-traction-specific navigation help. The existing `inputTrainUnitId` property switches this on when callers set their chart. Do not enable train filtering on an input rolling-stock curve. A chart with more than one kind of line, or with drawn section boundaries, gets a legend of the kinds below the plot: the `layer` property of a series names its kind, else a series whose name contains "planned" in any letter case is planned and drawn dashed, and any other is simulated. `TimetableTableWindow::setPresentation` accepts a concise heading and case/scenario context; `setRunProvenance` supplies those identities without changing CSV/PNG provenance.

The result windows cap their initial width/height to 90%/80% of the available screen and retain their chart/table navigation and export controls. A window that Run Results opens appears centred over the main window; while another such window is open, it opens 32 px below and to the right of the one that opened last, or at the top left of the screen when it would not fit there. The Export CSV... button is shown only in a window whose caller has set a CSV provider, so the input traction characteristic, which has none, has no CSV button. After a save in a diagram window, the status bar of the main window names the file for a few seconds. No button of a diagram or timetable window is the default button: Enter in the chart or the table starts no export and clears no selection. A button that has the focus is pressed with Space. The table still shows all nine columns with horizontal scrolling where needed. Disabled buttons and read-only fields inherit the existing stylesheet.

The input traction, route, blocking-time and compressed blocking-time callers provide explicit scope and essential interpretation warnings. The four per-train charts (speed/distance, speed/time, time/distance and simulated tractive effort/distance) and the delay chart give no warning. Their window title is the name of the chart and their context line reads `Run: <case> / <scenario>`; only the chart title, which a PNG export shows, has the run in brackets. Run Results groups diagram actions in a menu and keeps exports and baseline actions separate. Capacity results retain complete scope and method notes alongside the pair, compression and critical-block tables. The delay analysis window has the window title Delay analysis and names the run, with its scenario, and the baseline in its context. The capacity results, titled Capacity, and the capacity by area results, titled Capacity by area, give their result as the first line of the context. The capacity and delay analysis windows use `DialogLayout` for a screen-bounded scrollable body and fixed Close footer. CSV export and the compressed-chart action remain in the body rather than widening the footer. The creator acceptance path checks their bounded geometry, enlarged-font and long-context behavior, and table contents.

Inspector fields remain read-only. Signal member details use a light, wrapped text panel; long field values remain available through selection and tooltips. Editor docks use scrollable outer viewports to prevent their forms from enlarging the main window. Compact numeric fields show full precision during editing and preserve the stored value when an untouched field gains or loses focus.
