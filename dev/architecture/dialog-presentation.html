Custom dialog presentation contract¶

Use widgets/DialogLayout.h for new or migrated custom QDialog forms. Supply the name of the dialog as the heading and a short context once, and place fields, units, help, and inline status inside the body widget. Show help text with DialogLayout::setHelp(label, text) and inline status with DialogLayout::setStatus(label, severity, text), where DialogLayout::Severity is Neutral, Warning or Error. Both show the text as plain wrapped text in a label that has a parent widget (the dialog body or an editor panel), and an empty text hides the label. A label has either the help role or one status role, and a call can change it also after the dialog is shown. The helpers set the dialogHelp and dialogStatus properties that the stylesheet selects on. Neutral empty and successful states are not warnings. Keep labels associated with their fields and retain keyboard tab order.

DialogLayout::install(dialog, heading, context, body, buttons) transfers the body and button box to the dialog. It makes the heading the window title and does not repeat it inside the dialog, so the name shows once, in the title bar, and the body starts with the context line. It gives the context and body a resizable scroll viewport while keeping the button box outside it. The combo boxes and spin boxes in the body change with the mouse wheel only while they have keyboard focus (widgets/FocusWheel.h), so the wheel over a field scrolls the body; ChoiceComboBox and CompactDoubleSpinBox do the same wherever they are used, and the editor docks guard their fields from where the main window gives each dock its scroll area, which also covers fields that appear later. The footer buttons are styled again after the body is installed, because a caller names them and chooses the default before that, and a style cached by then misses the rules that name them. Keyboard focus entering the body scrolls the focused control into view. The scroll area itself takes no focus, so Tab never stops on it and a click on an empty part of the body leaves the focus where it is. The footer buttons follow each other in the focus chain in the order the footer shows them, so Tab and Shift+Tab visit the fields of the body and then each footer button once. The context is forced to plain text so authored names are never interpreted as markup; a window title is always plain text. Its size cap uses the current screen’s available geometry (90 percent of the width and 80 percent of the height); the optional rectangle supports deterministic tests. The dialog opens at the height its content needs, so the viewport scrolls only when the content is taller than that cap, and DialogLayout::fitWidthToContent makes it taller again after a change to the body. A message that setStatus or setHelp shows in a shown dialog does the same once the layout has made room for it, and the height counts every visible widget that a caller adds to the dialog layout. Other changes to a shown body do not make the dialog taller unless the caller calls fitWidthToContent, as the Run details toggle of the run review does. The body takes any height the dialog has beyond that, and the context line keeps the height of its text. Margins follow the dialog’s system font. Supply a QDialogButtonBox with task-appropriate roles and let Qt order its buttons for each platform. The helper does not connect buttons, select a default, validate, accept/reject, or mutate a model. It gives the focus to the first field of the body, a widget that Tab reaches other than a push button, a tool button or an item view, and without one to the default button: the button the caller made the default, else the first accept button, which the button box makes the default when the dialog is shown. Otherwise Qt gives the focus to the first button of the footer, Cancel on macOS and in GNOME, and a button takes the default while it has the focus. A caller that wants another first focus sets it after install. When a button that took the default loses the focus, the dialog gives the default back to that button, also when the caller chose it before the button box was in the dialog. In a footer laid out for macOS the footer buttons are not auto default, so a footer button that gets the focus leaves the default where it is, as in native dialogs; a push button in the body still takes the default while it has the focus. Elsewhere a footer button with the focus is the default. Space presses the focused button everywhere. The caller must explicitly wire acceptance and rejection, choose a safe default, and preserve its existing transaction/Cancel semantics. Never make a destructive action the Enter default. Use regular QFileDialog and QMessageBox unchanged rather than applying the custom layout to them.

The stylesheet retains transitional runReview* selectors for compatibility. Every QDialog, message boxes included, is one surface: the plain widgets, frames, labels, check boxes and scroll areas inside it take the colour of the dialog, so the body shows no box of its own, while fields, lists, tables and status labels keep their own faces. A group box in a dialog is a bold title over its fields, without a frame. The default button of every dialog footer and QMessageBox has the same filled face, hover, pressed, focus and disabled looks, so that the Enter default shows in every prompt. Interface style gives the colours and sizes. The default button differs by colour only and keeps the weight of the other buttons, because Qt sizes a button before a state rule applies and a bolder default text would be wider than its button. The disabled look applies throughout the application: disabled push buttons, combo boxes, line edits and spin boxes have a grey face, a light border and grey text in dialogs and main-window panels. A disabled default button in a dialog footer keeps its lighter grey. A read-only line edit keeps its read-only look when disabled. Disabled tool buttons and check boxes change only their text colour, except the toolbar buttons, the Open result view… button of Run Results and the Trains, Occurrences and Stations buttons of the result windows, which have the look of a disabled push button; checked tool buttons keep their checked look. A disabled menu entry has grey text. These rules restyle no other widget.

Callers¶

Run review, the case chooser, timetable-stop editing, blocking-time scope and capacity options use this layout. The delay analysis, capacity and capacity by area windows also use it, with a ResultFrame as the body (ResultFrame::installInDialog): the header names the run in one line, the tables lie at the left and a panel with the key figures, the filters and the CSV and diagram actions at the right, all in the scrollable body, and Close stays in the fixed footer. Run review separates its summary from expandable configuration details. The case chooser groups bundled and recent cases and keeps creation/import actions in a secondary menu.

Choice combos whose entries can be long imported names use widgets/ChoiceComboBox.h instead of a plain QComboBox; the timetable stop editor and the blocking-time scope and capacity options dialogs do. With it, long station or platform names never force a horizontal scroll bar. The field can shrink below its text, while its size hint lets DialogLayout::fitWidthToContent widen the dialog to the content within the same width limit as install. A selected text that is still wider than its field is drawn with its middle elided. The tooltip is the full current text, followed by the tooltip of the field when the caller sets one, and the popup list is as wide as its widest entry within 90 percent of the screen’s available width, eliding the middle of entries that still do not fit. The list shows each entry whole, also when the field has the focus. Callers set Qt::ToolTipRole on an item to explain it, as the timetable stop editor does for an invalid imported platform or a station that is not on the route. The route field of the Services dock and the target field of the Scenarios dock are also ChoiceComboBox fields. The tip of the route adds the stations of the selected route to the text of the field, and the tip of the target says what the incident type takes as its target: a signal or block for a signal failure, a train for a breakdown.

The stop table of the Timetable tab (TimetableStopsPanel::fitColumns) needs no horizontal scroll bar down to the minimum width of its columns. The platform, dwell and planned time columns take the width of their header or of a value of up to ten digits, whichever is larger, using the font metrics of the table. The station column takes the rest, at least six digits, and its whole header where the other columns can give up that room. In a table too narrow for that, the four narrow columns shrink in proportion. Cell text that does not fit is elided, and the tooltip of a cell holds the full text.

The reference-route chooser for the timetable graph and train paths is a list dialog (diagrams/RouteReferenceChoice.h): all choices are visible at once, rows wrap, and a double click or Enter accepts the selected row.

Composition membership uses the standard single-choice QInputDialog. File selection, warnings and confirmations retain QFileDialog and QMessageBox.

test_dialog_presentation_contract checks the case chooser and the Run simulation dialog in the built application; Checks says what it covers. Widget tests cover bounded dimensions, enlarged fonts, scrolling and keyboard access to the fixed footer, and the look of disabled controls inside and outside dialogs.

Inventory¶

Each row names the code that builds a dialog or prompt, so that a change to it finds the row to update. “Checked by” names the tests that open it. Where a row says that no test opens it, neither CTest nor a smoke script does.

Prompts with several buttons or a default that matters¶

Only test_updatetelemetrycontroller reads the default button of one of these prompts, the update prompt. test_dialoglayout draws the default button of a question box that it builds, except on Windows. It also checks, at the normal and at 1.5 times the font, that the default button of an update prompt with long button texts is wide enough for its drawn text.

EGTRAIN Is Available

UpdateTelemetryController::handleUpdateCheckFinished

Information icon. The main text is EGTRAIN <version> is available. You are using <installed version>., so that the offered version shows on macOS, which draws no title. Checks¶

The dialog sheet of 2026-10-17 shows each custom dialog before and after this contract on a Linux desktop.

These unit tests build dialogs without the application: test_dialoglayout for DialogLayout, test_casechooserdialog for the case chooser (the states of the list, the size limit at 1280 by 800 with a font 1.5 times larger and a 300 character case title in both groups, with no horizontal scroll bar, an elided row and the full path on opening, the default button, the arrow keys, Enter, double click, the reason of an unavailable row, the contrast of a selected row, one row for several spellings of one path, Escape and the tab order), test_aboutdialog, test_telemetryconsent, test_routereferencechoice, test_choicecombo for ChoiceComboBox, a copy of the timetable stop form and the wheel over the fields of a scrolled form, test_completedrun for the blocking-time scope and capacity options dialogs, test_diagramwindow, test_timetabletablewindow, test_areacapacitywindow, test_delayanalysiswindow and test_colorchoicebutton for the colour button.

test_completedrun and test_recoveryprompt also open the blocking-time scope dialog and the recovery prompt with the footer order and button focus policy of macOS, which a proxy style gives on the offscreen platform. They check the default button, the first focus, and Return while Cancel or Discard has the focus. test_aboutdialog opens About EGTRAIN in the same way and checks that Close is the default when it opens and again once the focus has left a link for the text, where Return closes the dialog. test_casechooserdialog checks, with the footer of Windows and Linux, which button is the default at each Tab stop. test_dialoglayout checks that Tab moves from one footer button to the next and that Space presses the focused one, and, with the footer layouts of Windows, macOS, KDE and GNOME, that Tab and Shift+Tab from a field of the body visit each footer button once in the order of the footer and then the field again. It also checks that the Run details toggle shows focus with the border of a dialog button, and, with a widget style that gives footer buttons an icon, that the buttons of a dialog footer and, outside Windows, of a message box show none, and that a spin box in a table cell gets the height it asks for.

test_dialog_presentation_contract checks the case chooser and the Run simulation dialog in the built application on the offscreen platform. It runs tools/e2e/creator_acceptance_smoke.sh --dialog-contract. The script starts the creator acceptance run, which saves a scene, and then starts tools/e2e/dialog_presentation_contract.py with the application and that scene. The scene_tool validations and the data checks of the default mode of the smoke do not run in this mode. CTest registers the test on macOS and Linux and not on Windows, because the scene comes from a Bash script. The pull request checks run it, and so do the validation and sanitizer jobs of the release workflow. It has the labels integration, gui and slow. The application reaches the checks through the hooks dialogShown and dialogClosed of MainWindowTestHooks, which showStartupChooser and RunController::showRunReview call around the dialog. tests/e2e/Dialogs.cpp answers them, and the release build does not contain it.

To run it by hand, set QEGTRAIN_APP and QEGTRAIN_SCENE_TOOL to the built programs, then run:

bash tools/e2e/creator_acceptance_smoke.sh --dialog-contract

For the case chooser the script checks that:

  • the first row is the group heading Bundled cases and is not enabled;

  • the row that is selected when the dialog opens, which is the first enabled row with a case path, is the first bundled case, whose name the script reads from the first folder of EGTRAIN/QEGTRAIN/Scenes;

  • Open is enabled;

  • the left button reads Continue while a case is loaded;

  • the loaded case and the scene revision are unchanged.

For the Run simulation dialog the script starts the application for each variant of the saved scene. The variants change which service runs enter during the period (including none), the warnings, the incident configuration, the length of the case and scenario names (including markup characters and an 18 point font) and the signalling area. Each variant runs with advanced details off and on, and the dialog is closed with the Cancel button and with Escape. The script checks:

  • the fact values, the details text, the context line, and the status text with its warning flag;

  • the validation counts and the incident configuration text, which appear only with advanced details on;

  • that Run simulation is the default button and has the first focus;

  • that the dialog stays within 90 percent by 80 percent of the available screen with the footer visible in the collapsed, expanded, scrolled and collapsed again states, and that the footer does not move when the body scrolls;

  • that Tab moves from the body to the footer and Shift+Tab moves back;

  • the state of the details toggle, and that it keeps the font of the dialog while tool buttons have the smaller font of macOS;

  • a size limit with the large font;

  • that Cancel and Escape start no run and leave the scene unchanged.

The script does not open the other dialogs of the inventory.

Only a person on a real desktop can check the native button order and the default and focus states on each platform, enlarged text, a 1280 by 800 window, and the prompts of the prompts table that no test opens.

Result windows¶

DiagramWindow::setPresentation(heading, context, warning, contextToolTip) supplies a short window heading, an optional scope context with an optional tooltip of its own, and an optional note that names only what is missing. Diagrams have no expandable technical-detail panels. The context is one line in the header, elided at the right, with the whole text in its tooltip. The warning wraps between the header and the chart without a fixed height limit, so long identifiers cannot clip it. Callers document calculation details in the user guide. The chart’s axes, samples, time formatting and export provider are unchanged. The window never guesses from chart titles: callers set the window title explicitly, and setChart clears the title of the chart. Authored IDs may contain |, so delimiter-based title parsing is unsafe. setRollingStockSubject(unitId) names the rolling stock unit whose input the chart shows; it hides the panel sections Trains and Selected, and its Key lists the curves by name. MainWindow::plotTrainUnitTraction sets it before the chart, and the main window finds the open curves of a unit by rollingStockSubject() to redraw, rename or close them. Do not enable train filtering on an input rolling-stock curve. The panel section Trains is a TrainKeyList, the train filter and colour key in one list, which setTrainServices groups by service. The section Key is a DiagramKey that lists the kinds of mark of the shown series in the pen and brush of the chart, and the plot has no legend: the keyKind property of a series names its kind, and an empty one leaves the series out; without it the layer property names the kind, else a series whose planned property is true is planned and drawn dashed, and any other is simulated. The name of a series is not read for this, because it holds the id of a train. A closed outline with inspectionFilled is a box with the brush of the area series of its kind, and with the pen of its keyPen property where it has one, keyMarker names the kind of the points of a series, such as Stop, and keyUpright draws the sample of a dwell upright. Simulated is left out while it is the only kind of line, and the section strip adds its own kinds. The blocking-time charts set keyKind to Blocking time, Critical block or Conflict with styleBlockingTime, which also gives the look of each kind and of its sample. The PNG export and Copy add the Trains and Key in a column at the right of the chart (DiagramWindow::exportedFigure). TimetableTableWindow::setPresentation accepts a concise heading and case/scenario context; setRunProvenance supplies those identities without changing CSV/PNG provenance.

The result windows cap their initial width/height to 90%/80% of the available screen and retain their chart/table navigation and export controls. A window that Run Results opens appears centred over the main window; while another such window is open, it opens 32 px below and to the right of the one that opened last, or at the top left of the screen when it would not fit there. The CSV… button is shown only in a window whose caller has set a CSV provider, so the input traction characteristic, which has none, has no CSV button. After a save in a diagram window, the status bar of the main window names the file for a few seconds. No button of a diagram or timetable window is the default button: Enter in the chart or the table starts no export and clears no selection. A button that has the focus is pressed with Space. The table still shows all nine columns with horizontal scrolling where needed. Disabled buttons and read-only fields inherit the existing stylesheet.

The input traction and blocking-time callers set a note only for what is missing. The route charts, the four per-train charts (speed/distance, speed/time, time/distance and simulated tractive effort/distance) and the delay chart set none. Every result chart has the name of its view as its window title and the run as its context, as <case> / <scenario>, and the chart has no title of its own; the blocking-time charts add their scope after the run, as <case> / <scenario> · <scope>, and the route charts and the delay chart their reference route, as referenceRouteText gives it. The PNG export and Copy draw the window title as the heading of the figure and the context below it. The table windows Timetable, Delay analysis, Capacity and Capacity by area name the run as <case> / <scenario> in their header, followed in Delay analysis by the delay baseline, in Capacity by the section and in Capacity by area by the area. Run Results groups diagram actions in a menu and keeps exports and baseline actions separate. Capacity results give their scope in the context and leave the method to the user guide, alongside the pair, compression and critical-block tables. The delay analysis window has the window title Delay analysis and names the run, with its scenario, and the baseline in its context. The capacity results, titled Capacity, and the capacity by area results, titled Capacity by area, give their result as key figures at the top of the panel. The capacity, capacity by area and delay analysis windows use DialogLayout for a screen-bounded scrollable body and fixed Close footer, through ResultFrame::installInDialog. The CSV export and the compressed-chart action lie in the panel, inside the body, rather than widening the footer. The creator acceptance path checks their bounded geometry, enlarged-font and long-context behavior, and table contents.

Inspector fields remain read-only. Signal member details use a light, wrapped text panel; long field values remain available through selection and tooltips. Editor docks use scrollable outer viewports to prevent their forms from enlarging the main window. Compact numeric fields show full precision during editing and preserve the stored value when an untouched field gains or loses focus.
