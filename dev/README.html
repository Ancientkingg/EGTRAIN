Run existing scenes¶

  • EGTRAIN releases

  • Getting started: from a download to a first run of the Paimpol case study, its results and two exported files.

  • How-to: recipes for opening and saving a case, fixing validation errors, editing a timetable or rolling stock, comparing a scenario with a baseline, moving around the network view, replaying a run, exporting results and converting a legacy case, and why a command is disabled.

  • Opening an .egscene case study

  • Updating EGTRAIN: the automatic and manual checks, consent, what an update does to an installed or portable copy, and the earlier builds that need a manual upgrade.

  • Glossary of application terms

  • Command-line options and scene_tool

  • Run output files

  • Sharing a live run: how to start a run with the live stream, a small client that reads positions and sends one command, the commands, and what to check when it does not work.

  • Amsterdam to Hilversum student case

  • How delays are calculated: the definitions of delay, how to read the Delay analysis window and its comparison against a baseline, the statistics files, the supported scope and the limits.

  • How capacity is analysed: the train chain window and the capacity by area window, with the choice of scope and period, the completeness rule, the governing resource and a figure reproduced by hand.

  • Inspecting diagrams: how to hover, select, zoom and pan in a result diagram, and how the timetable graph, the train-path graph and the blocking-time charts are drawn.

Create or edit scenes¶

  • Using EGTRAIN and authoring scenes: what the docks and windows show, the rules for editing and validating, and the scene files in a Reference part.

  • V1 scene property reference

  • Scene schema reference

  • Scene bundle format

  • V1 active-input migration matrix: what each family of legacy input files becomes in a scene, and which of them a run does not use.

  • Signalling levels and signalling areas

  • Assignment corridor

  • Assignment workflow

  • Feature status 2026-10-17: a dated snapshot of what works, what is only partly done and what is untested, with the evidence for each row and the gaps found.

A scene folder is the editable source of truth. An .egscene bundle packages its files for transport. Legacy import and export remain explicit interoperability actions; normal scene loading and simulation use the canonical model.

Develop or contribute¶

  • Getting started as a developer: the tools you need, a first build and run, a map of the sources, the path from opening a case to saving it, which checks to run, and a first change to a test.

  • Build and test guide: configure recipes for each system, common setup failures, test labels and smokes, where output goes, and CI.

  • Coding guidelines

  • Error handling: where exceptions are caught or escape, the fatal paths, what the user sees and what is logged for each failure, the safety nets, and the crashes seen in October 2026.

  • Documentation decision: how the docs are structured, built, checked and shipped in the app, the options compared, the screenshot process and the map of every page.

  • Code documentation investigation: the comment coverage per source folder, the legacy simulation core, the unstated units and conventions, dead or misleading comments, open questions and the order of the follow-up work.

  • QEGTRAIN source layout: the folders of EGTRAIN/QEGTRAIN and what each holds, the libraries and the renames.

  • Scene model design

  • Scene editor flow: how the editor creates, opens, validates, runs and saves a case, with the main window layout and the edit panes.

  • Signalling levels and signalling areas

  • External state sharing: the legacy -TSM and -RC channels, and the live stream with its contract version 1 (frames, units, ordering, sampling, compatibility, threads, commands and errors).

  • Usage and diagnostics wire contract

  • Custom dialog presentation contract: the rules for custom dialogs, how to build one with DialogLayout, which dialogs use it, and the checks that cover them.

  • Dialog sheet 2026-10-17: the custom dialogs before and after the shared presentation, side by side, as a dated record.

  • Result-window presentation seam: the contract for the heading, context and warning of the result windows, their size limits and the layout of the custom result dialogs.

  • Main window: the toolbar speed slider and its readout, the run duration in Run simulation, the lines at the top of Run Results, the first sizes of the Run Results and Case and Layers docks, and the look of tables, the progress bar and the Run Results buttons.

  • Network renderer style map: how the network canvas draws each element, with colours, sizes and contrast ratios.

  • Historical track presentation: the original renderer used as the visual reference, the only intentional differences from it, the captures that compare the two renderers, and how its drawing distances convert to scene units.

  • Playback profiling: the opt-in tool that measures GUI playback of the Copenhagen case, with its protocol, what it measures and its decision rule.

  • Peak-memory baselines: how to record the peak memory of the Copenhagen and Milano-Brescia runs on macOS, and the baselines recorded so far.

  • Qt 6 migration study: what moving from Qt 5.15 to Qt 6 takes, with the incompatible APIs, packaging, CI, platforms, licences, estimates and an order of work.

History and records¶

Each of these pages records one conversion, comparison or rehearsal. They are not guides for the current release.

  • V1 native cutover report: the conversion of the cases that were committed then to canonical V1 scenes, with the source corrections and the legacy material that was not migrated.

  • Original-case native runtime parity: the comparison of the output of the Netherlands, Paimpol, Copenhagen and Milano-Brescia cases before and after the native runtime cutover, and the differences found.

  • Release rehearsal 2026-08-23: the record of one release rehearsal, with the result for each platform.

  • Release rehearsal 2026-10-17: the record of the packaged rehearsal on macOS, Windows and Linux, with the result for each checklist row, the defects and the rows left to the owner.
