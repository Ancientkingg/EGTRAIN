Release Testing Checklist¶

Use this checklist before a student release. Record the tag, commit, platform, OS version, package name, case-study bundle, result, and linked defect for every rehearsal.

Candidate¶

One rehearsal belongs to one candidate: one commit. Take every file from one source and never mix files of different runs or releases. The candidate comes from one of two sources.

  • One run of the Release workflow, either a manual run or the run of a pull request to production. The run has these artifacts:

    • QEGTRAIN-macos-arm64, holding EGTRAIN-<version>-macOS-arm64.dmg

    • EGTRAIN-windows-x64-installer, holding EGTRAIN-Setup-<version>-x64.exe

    • EGTRAIN-windows-x64-portable, holding EGTRAIN-Portable-<version>-x64.zip

    • QEGTRAIN-windows-x64-payload, holding the files of the Windows package

    • QEGTRAIN-linux-x86_64, holding QEGTRAIN-linux-x86_64.AppImage

    • EGTRAIN-scenes, holding the .egscene files

    The run page offers each artifact as a download that arrives in an outer zip. Unpack that zip once to reach the file named above. The outer zip of QEGTRAIN-windows-x64-payload holds the files of the Windows package themselves. The installer and the portable archive are made from them, so rehearse those two and not the payload. A run has no release job, so it has no update-manifest.json and publishes no release.

  • The assets of one published release, made by a push to production or by a v* tag. A release holds the application assets, the case-study bundles and update-manifest.json that the next section lists, and nothing else. It stays a draft until all of them are uploaded. A v* tag that contains a hyphen is published as a prerelease: the updater never offers it, and its version is the number before the hyphen.

A manual run and the run of a pull request build the CMake baseline version, not a release number. The version shown by About EGTRAIN for such a candidate is therefore the baseline, and the names of the installer and of the portable archive carry it. Record that version; step 1 says where the entry is.

A fix after a failed row needs a new candidate and a new record.

Before a release, check that the authors in CITATION.cff are still correct.

Automated release evidence¶

The release is ready to rehearse only when the version, validation, sanitizer and the package jobs of the Release workflow (macOS, Windows, Finalize Windows, Linux and Rehearse Linux) are green. The release job needs all of them. CI and release branches describes what the workflow does.

Expected application assets:

  • EGTRAIN-<version>-macOS-arm64.dmg

  • EGTRAIN-Setup-<version>-x64.exe

  • EGTRAIN-Portable-<version>-x64.zip

  • QEGTRAIN-linux-x86_64.AppImage

<version> is the version of the release without the leading v. The releases up to v1.0.2 have QEGTRAIN-macos-arm64.zip for macOS and QEGTRAIN-windows-x64.zip for Windows instead of the disk image and the two Windows names above.

Expected case-study assets:

  • Netherlands.egscene

  • Paimpol.egscene

  • Copenhagen.egscene

  • Milano_Brescia.egscene

  • Assignment_Gvc_Gdg_Ut.egscene

  • Amsterdam_Hilversum_Student.egscene

A published release also has update-manifest.json. Confirm the workflow validates all the bundles and publishes exactly the application assets and the case-study assets above and the update manifest.

What the jobs prove today:

  • The Full validation job builds the project with tests on macOS and runs CTest, which holds the end-to-end smoke tests. The Sanitizers job runs CTest again in a debug build with sanitizers.

  • In the Package macOS job, no Mach-O file of the app names a path under /opt/homebrew or /usr/local in otool -L, otool -D or otool -l, and the app has a valid signature, which is ad hoc unless the environment macos-signing holds a Developer ID certificate (see macOS releases). tools/release/macos_build_paths.py deletes such run paths and install names before the signature (step Remove build machine paths) and fails the job when one is left (step Verify the app is self-contained). The job removes the virtual keyboard input plugin with the Quick and QML frameworks, and the WebP and TIFF plugins with their libraries, from the app before the signature, and fails when one of them is in the app or when the cocoa platform plugin, the SVG icon engine or the macOS style is missing. The app holds scene_tool. scene_tool validates the Paimpol scene of the app, and the app runs Paimpol without the GUI from Contents/Resources/Scenes to End of Simulation. The job starts a copy of the app with tools/release/package_start_smoke.py (step Start the package), which first checks that every dependency of the app is a system library or a file inside the app and that every library inside the app is loaded by some file. The job prints the number of files and bytes of the app before and after the removal in its job summary. It also packs and validates the six bundles. Then it builds EGTRAIN-<version>-macOS-arm64.dmg from the signed app, mounts the image read-only, checks that the volume holds only QEGTRAIN.app, the link Applications and the hidden Finder layout file .DS_Store, which must equal tools/release/dmg/DS_Store, that the app in the image and a ditto copy of it have a valid signature, that the property list of the app in the image declares .egscene as its one document type, which conforms to public.data and so claims no archive type, and that the copy runs Paimpol to End of Simulation.

  • The Package Windows job checks that these files exist: QEGTRAIN.exe, egtrain_update_helper.exe, Qt6Core.dll, Qt6Gui.dll, Qt6Widgets.dll, Qt6Charts.dll, Qt6Svg.dll, Qt6Network.dll, Qt6Help.dll, Qt6Sql.dll, platforms/qwindows.dll, imageformats/qsvg.dll, iconengines/qsvgicon.dll, styles/qmodernwindowsstyle.dll, sqldrivers/qsqlite.dll, a libzmq DLL, scene_tool.exe and Scenes/Paimpol. It fails when the software OpenGL, Direct3D or DXC compiler libraries, Qt Quick, QML or virtual keyboard files or vc_redist.x64.exe are in the package. It copies the Visual C++ runtime DLLs that the program files import next to QEGTRAIN.exe and fails when a program file imports a DLL that is neither in the package nor part of Windows (tools/release/pe_imports.py). The Finalize Windows job runs the same check on the extracted portable archive. The Package Windows job prints the number of files and bytes of the package in its job summary.

  • The Finalize Windows job compiles the installer from that package directory with Inno Setup and runs tools/release/installer_smoke.ps1 on the runner. The script checks that the installer asks for no elevation in its manifest. A silent install into a chosen folder leaves one uninstall entry for the current user and none for the machine, a Start Menu shortcut, no desktop shortcut, the files of the package with the same bytes, the marker file installed-by-setup.ini and one uninstaller, and package_start_smoke.py starts the installed copy. The install registers the .egscene file type for the current user, with the installed QEGTRAIN.exe as the program that opens it, and the uninstall removes it together with the entry, the shortcut and the files, and leaves a file beside the folder in place. An install with the desktop task creates the desktop shortcut and the uninstall removes it. A second installer of the next patch version installed over the first, in the default folder, leaves one entry, one folder and the higher version, replaces the Scenes folder and deletes the Qt 5 files that an installation of version 1.0.3 or older holds. A copy of the same directory, started as a portable copy is, registers no file type. The job then writes the portable archive from that directory, extracts it and starts the extracted program with the same start script.

  • The Package Linux job extracts the AppImage and checks the executable, the update helper, Scenes/Paimpol, the icon, AppRun and the Qt libraries. It then starts the extracted image through its AppRun on a virtual display, after it has checked that every Qt and ZeroMQ library of the programs and plugins comes from the image and not from the runner.

  • The Rehearse Linux job runs the steps 1 to 9 of the clean-install rehearsal on the AppImage that the Package Linux job uploaded. It runs on every package run, so the release run rehearses the frozen candidate. The runner is a GitHub Ubuntu 24.04 machine with a virtual display, a D-Bus session and the AT-SPI accessibility bus. The job installs no Qt package. It extracts the image, packs the Paimpol scene of the image into a .egscene bundle with the scene_tool of the image, and runs tools/release/linux_rehearsal.py. The bundle comes from the image because the macOS job, which uploads the case-study bundles, would end this job after the Windows jobs. The script starts the image through its AppRun with a new home directory and no QEGTRAIN_ variable, and drives the real menus and dialogs through AT-SPI, with xdotool only for typing and for giving the keyboard to a field or a table cell. The release package has no test hook. Each step prints STEP n PASS or STEP n FAIL with what it saw, and the job stops at the first step that fails. The script also fails when the area of the buttons Zoom In and Zoom Out of the toolbar, which show an icon and no text, has one colour, which shows that the SVG icons are drawn, and when typed text does not reach a text field or a table cell. The screenshots of the steps, the output of the application and the log of the script are the artifact linux-rehearsal-evidence of the run, also when a step fails. The artifact is for diagnosis and is not a release asset. Record the result of the steps 1 to 9 on Linux from this job, and label it as a run on a GitHub Ubuntu runner with a virtual display. The job does not cover dragging a bundle from a file manager (row R2), a real desktop session, the questions that a desktop environment asks at the first start, the file dialog of a desktop environment (the job uses the dialog of Qt) and the rows R1 and R3 to R12.

  • Each package job also runs the update helper tests (ctest -R '^test_update(helper|preparation)$', step Verify update helper transaction).

  • The Package Windows job also makes one HTTPS request to the GitHub release list from a copy of the package, with only the Windows directories on PATH (step Check HTTPS from the package). It shows that the update transport completes an HTTPS request with the Qt files of the package and no Qt or vcpkg directory on PATH. It does not show the update check of the application on a clean machine, which row R8 covers.

  • The Package macOS job starts a copy of the app that goes into the disk image, the Package Windows job starts a copy of the directory it uploads, and the Package Linux job starts the extracted AppImage, all with tools/release/package_start_smoke.py (step Start the package). None of them makes a CSV or PNG export, because a release build has no test hooks to ask for one. The Windows leg of the CMake workflow starts a Windows package assembled in that workflow (step Start an assembled Windows package). Except for the installer and the portable archive of the Finalize Windows job and the extracted AppImage of the Rehearse Linux job, none of this starts the released file itself, and only the Rehearse Linux job shows how the SVG icons look or typing into text fields, on Linux.

The Finalize Windows job runs as an administrator on a machine that has the Visual C++ runtime. It does not show that a standard user installs without an elevation request, that the package starts on a machine without the redistributable (the import check shows that the runtime DLLs are in the package, not that a clean machine loads them), or how Windows presents the unsigned installer and the entry in the list of installed apps. The job reads the registry keys of the .egscene file type but opens no file, so it does not show that a double-click on a .egscene file in Explorer opens EGTRAIN (#416); row W7 does. The rows W1 to W9 below cover the rest of what the job cannot.

The Package macOS job reads the document type from the property list of the app in the disk image but opens no file. It does not show that Finder knows the .egscene file type of the installed app or that a double-click opens a file in EGTRAIN, with EGTRAIN closed or open (#416); the rows M1 to M3 do.

Apart from the Rehearse Linux job, none of this shows the GUI student workflow.

Clean-install GUI rehearsal¶

Run this section on macOS, Windows, and Linux from the downloaded package and a downloaded bundle of one candidate. Use a clean machine, VM, or user account without a source checkout, Qt, CMake, or other development dependencies in the test path. The test account must not have QEGTRAIN_ variables set: any QEGTRAIN_E2E_ variable, QEGTRAIN_DISABLE_UPDATES and QEGTRAIN_AUTOSTART switch the update entries off and are not part of a student launch.

On Linux, the steps 1 to 9 run in the Rehearse Linux job of every package run, on a GitHub Ubuntu runner with a virtual display, and need no machine of their own. Automated release evidence says what that job does and does not cover.

On Windows there are two downloads, and each one gets this section. Row W2 below installs the installer and runs the steps on the installed copy. Row W6 unzips the portable archive and runs the steps and the R rows on that copy. Rows R9 and R10 run on the portable copy, because they replace the installation. Row W8 runs the in-app update on the installed copy. Both copies keep their settings in the profile of the account, not in their folder, so the question of R7 is asked at the first start in W2 and not again in W6.

Before step 2. Make a byte-for-byte copy of the downloaded bundle in another folder and note the modification time of the original. While the downloaded bundle is the open case, File > Save Scene and the Save button of the Unsaved Scene message write into the open bundle. The edit of step 4 is therefore saved only through step 5, Save Case Study As….

Installed examples are protected separately: Save asks for a new bundle in a user folder. This does not protect an ordinary downloaded bundle from an in-place save. Row R11 checks the installed-example path.

  1. Launch the downloaded application through the platform’s normal GUI path. On macOS that path is: open the disk image, drag QEGTRAIN.app onto Applications, eject the image and open the copy in the Applications folder. Record:

    • on macOS, what the window of the disk image shows. The layout file asks for an icon view with large icons, without toolbar, sidebar, path bar and status bar, with QEGTRAIN.app on the left and Applications on the right at the same height;

    • the version shown by About EGTRAIN, in the Help menu or, on macOS, the application menu;

    • any operating system warning shown at the first launch, with its text. An ad hoc macOS package is refused at the first start (row M4), and a notarized one is expected not to be (row M5). Do not assume a warning on Windows or Linux; record what appears;

    • the title of every dialog shown before the main window can be used;

    • anything you had to install or change to make the package start. On Windows, say whether the Visual C++ redistributable was installed before the test. The package holds the runtime DLLs next to QEGTRAIN.exe, but the jobs run on machines that have the redistributable, so they do not show whether a clean machine starts without it.

    After the main window appears, the application shows the case chooser Open a Case. Its group Bundled cases lists the cases found in a Scenes folder next to the executable or in the working directory, in ../Resources/Scenes or in ../share/EGTRAIN/Scenes relative to the executable. Note what the chooser lists. Close it before step 2 with the button that keeps the current case: Continue when a case is loaded and Cancel when none is.

  2. Open a downloaded .egscene through File > Open Case Study….

  3. Confirm the network renders. Show Loaded Data with View > Loaded Data (the entry is checked while the dock is shown) and confirm that it shows identity, versions, category counts, scenarios, validation, runtime, and result readiness.

  4. Select or edit a scenario and confirm the run review names that scenario.

  5. Use Save Case Study As… to write a working copy outside the package. The dialog proposes the downloaded bundle itself: give the copy a new name in another folder. Confirm the downloaded source bundle is unchanged. Compare the original with the copy from before step 2 and check the modification time of the original against the one you noted. On macOS and Linux, run cmp <original> <copy>, which prints nothing when the files are equal. On Windows, run fc /b <original> <copy> in a command prompt, not in PowerShell, where fc is another command; it reports no differences when the files are equal.

  6. Run a short simulation from the working copy: choose Simulation > Run, then Run simulation in the review window.

  7. Open timetable, delay, speed, and blocking-time results where the case supports them. Confirm timetable output separates planned and simulated arrival and departure values.

  8. Export one CSV and one PNG to a user-writable directory.

  9. Quit, relaunch, and reopen the working copy. Confirm saved canonical and scenario edits remain. Compare the downloaded source bundle with its copy again, as in step 5, and check its modification time.

R9 In-app update

R10 Installation that cannot be updated in place

The update dialog has no Update and Restart button. Its text says The packaged installation is not writable. Use the release page to update manually. On macOS, a copy that runs from a mounted disk image shows EGTRAIN is running from a read-only location, such as a disk image. Move EGTRAIN to the Applications folder first. Use the release page to update manually. instead.

All

R11 Save an installed example

Copy the installed scene folder before testing, then open the installed example through Open Case, edit it, and choose Save Scene. Cancel once, then save a new .egscene outside the installation. Reopen and edit the installed example before repeating through Save in Unsaved Scene. Try an installed folder as the destination of Save Scene As Folder…, and a file inside it through Save Case Study As….

The dialog starts in the Documents folder, or in the home folder when there is none, and not in the installation. Cancel retains the edit and current case; a successful save makes the new bundle current. Installed destinations are rejected. The original folder’s file paths and bytes remain unchanged. A later edit saves in place to the external bundle.

All

R12 Bundle of the previous release

Download one .egscene bundle from the assets of the latest stable release before the candidate, for example Paimpol.egscene. Open it in the application under test with File > Open Case Study… and run a short simulation as in step 6.

The bundle opens without a version message, and the simulation runs to its end. Record the tag of the release. A message that the scene is older, newer or unsupported is a finding, unless the candidate deliberately drops support for that format.

All

Notes on the update rows:

  • The update check looks at the latest stable release. A draft or a prerelease is never offered. Update and Restart is offered only for a stable release that is newer than the running version, holds update-manifest.json and the package of the platform, and only where the installation can update itself. Application updates describes the update.

  • A candidate that carries the baseline version is offered the latest published stable release when that is newer. Do not update it in place before the other rows of that platform are done; R9 does that on purpose, last. With automatic checks on, the same dialog also appears at the start of the application; choose Later until R9.

  • Stop Checking switches automatic checks off. Use it only to record that button, and only if R7 does not have to be repeated on that account.

  • Precondition of R9 and R10: Help > Check for Updates… on the installation under test offers a newer stable release with the button Update and Restart. The installation under test is the candidate itself when its version is lower than the latest stable release. That is so for a manual run whenever a stable release newer than the baseline exists. Otherwise install an older stable release from its downloaded asset: it is the one exception to the rule of one source, so record its tag. Put the installation in a folder the test account can write to. Run R10 before R9, or on a separate copy of the package, because R9 replaces the installation.

  • R12 uses a bundle of an earlier release, which is an exception to the rule of one source, like R9; record its tag. It shows that the scenes released before still open in the candidate. If the candidate changes the scene format, add one of its own bundles to the scene fixtures once the release is published, as Unit Tests says. Mark R12 not applicable, with the reason, when no earlier stable release with bundles exists.

  • R9 installs the latest published stable release, not the candidate. It shows the update path of the installed version and says nothing about the contents of a manual candidate.

  • On Windows run R9 and R10 on the portable copy. In an installed copy, Update and Restart runs the Setup of the newer release and does not replace the installation folder; W8 covers that. The older stable release for R9 on Windows is QEGTRAIN-windows-x64.zip, a portable archive too.

  • Mark R9 or R10 not applicable, with a reason for this case, when no newer stable release is offered, when no older stable release that has the update entries can be installed for R9, or when the account cannot be denied write access for R10.

macOS app¶

Run these rows on macOS with the disk image of the candidate, and mark them not applicable on Windows and Linux. Use the copy of QEGTRAIN.app that step 1 of the clean-install rehearsal put in the Applications folder, and downloaded .egscene files. Run M4 or M5 as the first launch of step 1, then M1, M2 and M3 in this order. The signature of the copy in the Applications folder shows which of M4 and M5 applies. Run codesign -dvv /Applications/QEGTRAIN.app before the first launch; it does not start the app. Signature=adhoc means M4, and the line Authority=Developer ID Application: means M5. Mark the other row not applicable, with that reason. A Developer ID signature without a ticket, where xcrun stapler validate fails, is neither M4 nor M5: record it as a finding on the signing configuration. macOS may need a moment to learn the file type of a new app. If Finder does not know it yet, record that and what you did before it did, and go on with Open With.

M1 File type in Finder

Quit EGTRAIN. In Finder select a downloaded .egscene file and choose File > Get Info. Note the Kind and the application under Open with. Do the same for a .zip file. Then Control-click the .egscene file and open Open With.

Kind reads EGTRAIN Case Study and Open with names QEGTRAIN, which the Open With menu lists. Record the icon that Finder shows for the file. The .zip file keeps the application it had, and EGTRAIN is not the one that opens it. If Finder shows another Kind or application, record it, and whether choosing QEGTRAIN under Open with and Change All… corrects it.

macOS

M2 Open a case study by double-click

With EGTRAIN closed, double-click a downloaded .egscene file in Finder. Then change a value and double-click a second .egscene file: answer Cancel, double-click again and answer Don’t Save, which is Discard, and never Save. Last, quit EGTRAIN, start it from the Applications folder, leave Open a Case open and double-click a file.

The first file opens in EGTRAIN, and Open a Case does not open first; record it if it does. The second double-click brings the open window to the front and asks about the unsaved changes. The box has no title on macOS and reads The current scene has unsaved changes., and its buttons are Save, Cancel and Don’t Save, Qt’s native names for Save, Cancel and Discard. No second EGTRAIN icon appears in the Dock and no second window opens. Cancel keeps the open case and the edit, and the status bar reads Open canceled. Current scene retained. After Don’t Save the second file is open, and both files are in File > Recent Scenes. With Open a Case open, that window closes and the file opens. Record any question that macOS asks, with its text.

macOS

M3 Double-click a damaged file and a special path

Rename a plain text file to something.egscene. Put a copy of a bundle in a folder whose name and file name contain accented letters (for example é or ü) and one character outside the Latin alphabet. With EGTRAIN closed, double-click the damaged file, quit EGTRAIN, and double-click the bundle. With EGTRAIN open on another case, double-click the damaged file and then the bundle.

Record the message title and text for the damaged file, and which case and which window are shown after it. EGTRAIN does not crash, does not change the file and does not list it under File > Recent Scenes. With EGTRAIN open, the case that was open stays after the damaged file. The bundle opens each time.

macOS

M4 First start of an ad hoc build

Run it as the first launch of step 1 on an ad hoc candidate. Download the disk image with a browser, from the run page or the release page, so that macOS knows it came from the internet. Open it, drag QEGTRAIN.app onto Applications, eject the image and open the copy from the Applications folder in Finder. Use no terminal command that removes the download mark or changes Gatekeeper.

Record every dialog with its title, text and buttons. The first start is refused with the dialog "QEGTRAIN" Not Opened, whose buttons are Move to Trash and Done, and which has no Open button. System Settings > Privacy & Security shows, in the section Security, "QEGTRAIN" was blocked to protect your Mac. with the button Open Anyway. Open Anyway opens the dialog Open "QEGTRAIN"? with Move to Trash, Open Anyway and Done, and its Open Anyway asks for an administrator’s name and password. Record whether EGTRAIN starts after that and which dialog, if any, comes next. Another dialog or another order is a finding: record its text.

macOS

M5 First start of a notarized build

Run it as the first launch of step 1 on a Developer ID candidate. Download, copy and open the disk image as in M4. Before the first launch run xcrun stapler validate /Applications/QEGTRAIN.app, which must succeed.

EGTRAIN starts through the normal Finder path. The only dialog before the main window is the confirmation that macOS asks for an app that was downloaded: record its title and text. No Open Anyway, no visit to System Settings, no administrator password and no terminal command is needed. If one is, M5 fails, whatever the package job reported.

macOS

M6 Folder access questions

On an account that has never run EGTRAIN, start the app from the Applications folder, close Open a Case and choose File > Open Case Study…. Cancel, choose File > New Case Study… and choose File > Open Case Study… again. Last, in the file dialog choose lume or your home folder in the sidebar and write down what macOS asks.

The first two file dialogs open in the Scenes folder of the app without any question about Desktop, Documents or Downloads. The question "QEGTRAIN" would like to access files in your Desktop folder., and the same for Documents and Downloads, appears only when the file dialog lists your home folder, which it does in the last step. Record each question with its text and the step that caused it. Any question in the first two dialogs is a finding.

macOS

M7 Documentation pictures

This row needs no package. In a checkout of the candidate commit, build with EGTRAIN_BUILD_TESTS=ON as in Documentation pictures and run bash tools/docs/capture_screenshots.sh --check.

The script prints every picture matches docs/images. Otherwise it lists the pictures that changed. Retake them with bash tools/docs/capture_screenshots.sh, look at each, and commit them with the release, or record why the difference is expected.

macOS

Windows installer and portable archive¶

Run these rows on Windows with the installer and the portable archive of the candidate, and mark them not applicable on macOS and Linux. Use an account that is not an administrator, on a machine without development tools and without a copy of EGTRAIN. W2 to W5 follow each other on that account, and W7 and W9 run between W2 and W3. W5 and W8 need the Setup of an older version: it is the one exception to the rule of one source besides R9, so record where it came from. Run W6 after the last uninstall, so that the list of installed apps shows only what the archive itself adds.

Row

What to do

What must be seen or recorded

Platforms

W1 Windows assets

Open the release page or the run page of the candidate. For a published release also open update-manifest.json.

EGTRAIN-Setup-<version>-x64.exe and EGTRAIN-Portable-<version>-x64.zip are both there with the version of the candidate in their names. In the manifest of a published release the entry windows-x64 names the archive and the entry windows-x64-installer names the installer, and the size of each equals the size of the downloaded file.

Windows

W2 Install

Double-click the Setup. Read the licence page and accept the licence. Keep the default folder and leave the desktop shortcut box unticked. When it has finished, start EGTRAIN from the Start Menu and run the steps 1 to 9 of the clean-install rehearsal on this copy.

No prompt asks for an administrator password or for confirmation to run as administrator. The unsigned Setup shows the SmartScreen dialog Windows protected your PC (Microsoft Defender SmartScreen prevented an unrecognized app from starting. Running this app might put your PC at risk.); More info shows Publisher: Unknown publisher and Run anyway, which starts Setup (see Installing EGTRAIN). Record any other warning, and any wording that differs, as shown. The first page shows the GNU General Public License version 3, and Setup goes on only after the licence is accepted. The folder page offers %LOCALAPPDATA%\Programs\EGTRAIN. The Start Menu has the entry EGTRAIN. The list of installed apps in Windows Settings has EGTRAIN: record the version, which must be the one of the candidate, and the publisher. There is no desktop shortcut. Nothing is installed below Program Files. The installation folder holds LICENSE.

Windows

W3 Uninstall

Note the path of the working copy and of the exported CSV and PNG files, which lie outside the installation folder. Remove EGTRAIN from the list of installed apps in Windows Settings.

The entry, the Start Menu entry and any desktop shortcut are gone. The installation folder is gone, or holds only files that you or the program created in it. The working copy, the exported files, the downloaded bundles and the run output below the application data folder are unchanged. A .egscene file no longer opens in EGTRAIN.

Windows

W4 Reinstall

Run the same Setup again, and this time tick the desktop shortcut box. Start EGTRAIN from the desktop shortcut.

The SmartScreen dialog appears again and is passed with More info and Run anyway. It installs as in W2, with one entry in the list of installed apps and one Start Menu entry. The shortcut starts EGTRAIN. The question of R7 is not asked again, and the working copy opens: the settings and the files outside the folder survived W3.

Windows

W5 Upgrade

Uninstall as in W3. Install the older Setup, start EGTRAIN and leave it open, then run the Setup of the candidate over it. When it has finished, start EGTRAIN, open About EGTRAIN, and uninstall once more as in W3.

The first uninstall removes the desktop shortcut of W4 with the rest. Setup offers to close the running EGTRAIN and finishes when it is closed. Afterwards the list of installed apps has one EGTRAIN entry with the version of the candidate, there is one Start Menu entry, the installation folder is the same and no second folder named like it stands beside it, and About EGTRAIN shows the version of the candidate. The last uninstall removes everything as in W3. Mark W5 not applicable, with the reason, when no older Setup exists: the Finalize Windows job has installed a second Setup over the first on the runner.

Windows

W6 Portable archive

Unzip EGTRAIN-Portable-<version>-x64.zip into a new empty folder, for example with Extract All in Explorer. Start QEGTRAIN.exe by double-click. Run the steps 1 to 9 of the clean-install rehearsal and the R rows on this copy, except R7, which W2 has seen.

No prompt asks for administrator rights. Record any warning at the first start, with its text. The list of installed apps and the Start Menu show no EGTRAIN, and no shortcut was made. The folder has no installed-by-setup.ini and no uninstaller. Deleting the folder after closing EGTRAIN removes the copy.

Windows

W7 Open a case study by double-click

Run it right after W2. Close EGTRAIN and double-click a downloaded .egscene file in Explorer. With EGTRAIN open, change a value and double-click a second .egscene file.

Explorer shows the type name EGTRAIN case study and the EGTRAIN icon for the file. The first file opens in EGTRAIN. The second opens in the window that is already open, after the question about unsaved changes, and no second window appears. If Windows asks which program to use, record the question.

Windows

W8 In-app update of an installed copy

Meet the precondition of R9 with an installed copy: install the Setup of an older stable release, start EGTRAIN, choose Help > Check for Updates… and then Update and Restart. Uninstall as in W3 afterwards.

The dialog text says that Update and Restart runs the EGTRAIN installer. No Setup window and no prompt for an administrator password appears. EGTRAIN closes, starts again by itself and shows the box EGTRAIN was updated to version <version>. The list of installed apps has one EGTRAIN entry with the new version, there is one Start Menu entry, the installation folder is the same, and a .egscene file still opens in EGTRAIN. Record whether the desktop shortcut of an earlier install is still there. The hidden folder .qegtrain-update-* next to the installation is gone about 20 seconds after the start. Record any other message, with its text. Mark W8 not applicable, with the reason, when no older Setup that updates through the installer and no newer stable release that lists the installer in its manifest exist.
