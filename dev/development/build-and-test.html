Build And Test¶

Run configure, build, and test commands from the repository root. Run the application itself from EGTRAIN/QEGTRAIN so relative scene paths resolve.

Requirements¶

  • CMake 3.16 or newer

  • C++17 compiler

  • Qt 5.15 Core, Gui, Widgets, Charts, and Svg

  • ZeroMQ, cppzmq, and nlohmann-json

  • Python 3.9 or newer, found by find_package(Python3) at configure time; CTest runs its Python tests with that interpreter. On Windows, set PYTHONUTF8=1 for local runs so scripts read program output as UTF-8.

Qt Svg is required by the application and must be available with the other Qt modules.

Supported toolchains, as used by CI:

  • macOS: Homebrew Qt 5 and the packages in the configure example below.

  • Windows 10 or 11, x64 only: MSVC (Visual Studio 2019 or newer), Qt 5.15 msvc2019_64 with QtCharts, and vcpkg zeromq cppzmq nlohmann-json for the x64-windows triplet. 32-bit Windows is not supported.

  • Linux: Ubuntu (the ubuntu-latest runner image) with the apt packages in the configure example below.

Configure¶

cmake -S . -B build -DEGTRAIN_BUILD_TESTS=ON

On macOS with Homebrew Qt 5:

brew install qt@5 zeromq cppzmq nlohmann-json
cmake -S . -B build -DEGTRAIN_BUILD_TESTS=ON -DCMAKE_PREFIX_PATH=/opt/homebrew/opt/qt@5

On Ubuntu:

sudo apt-get update
sudo apt-get install -y build-essential cmake git python3 \
  qtbase5-dev qttools5-dev qttools5-dev-tools libqt5charts5-dev libqt5svg5-dev libqt5network5 \
  libzmq3-dev cppzmq-dev nlohmann-json3-dev
cmake -S . -B build -DEGTRAIN_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Release

In a root shell, such as a plain ubuntu:24.04 container, sudo is not installed: leave it out.

On Windows, from a Visual Studio developer PowerShell, with the vcpkg packages installed and the Qt 5.15 msvc2019_64 directory as CMAKE_PREFIX_PATH:

vcpkg install zeromq cppzmq nlohmann-json --triplet x64-windows
cmake -S . -B build -DEGTRAIN_BUILD_TESTS=ON `
  -DCMAKE_TOOLCHAIN_FILE="$env:VCPKG_INSTALLATION_ROOT/scripts/buildsystems/vcpkg.cmake" `
  -DVCPKG_TARGET_TRIPLET=x64-windows `
  -DCMAKE_PREFIX_PATH="C:/Qt/5.15.2/msvc2019_64"

CMake looks for Qt 6 first and uses Qt 5.15 when it finds no Qt 6. Qt 5.15 is the supported build and the one the release packages use. CI also builds and tests with Qt 6.8.3 on all three platforms, and a pull request must pass those jobs too. The package check builds the packages with Qt 6.8.3 as well. CMake searches a folder in CMAKE_PREFIX_PATH before the system folders, so the examples above use Qt 5 even when Qt 6 is installed elsewhere. To try Qt 6, configure a separate build folder with CMAKE_PREFIX_PATH set to the Qt 6 folder, for example ~/Qt/6.8.3/macos. With Homebrew, add the keg folders of the other libraries, such as /opt/homebrew/opt/zeromq, not /opt/homebrew: the headers of a linked qt@5 there would hide those of Qt 6. Qt 6.8.3 links the AGL framework, which the macOS 26 SDK no longer has; add -DWrapOpenGL_AGL="$(xcrun --show-sdk-path)/System/Library/Frameworks/OpenGL.framework" to link the OpenGL framework in its place. When one prefix holds both versions, such as /usr on Ubuntu, add -DQT_DIR=/usr/lib/x86_64-linux-gnu/cmake/Qt5 to choose Qt 5. QT_DIR in build/CMakeCache.txt shows which Qt a build folder uses.

The Visual Studio generator is multi-config: choose the configuration when building and testing, as in the next two sections.

The repository has no Visual Studio solution or project file. To work in Visual Studio, open the repository folder as a CMake project (File > Open > Folder) and give its CMake settings the toolchain file, the triplet and the prefix path of the command above. Choose an x64 configuration and QEGTRAIN.exe as the startup item. A configure for 32-bit Windows stops with a message that names x64 as the only supported platform.

Build¶

cmake --build build

With a multi-config generator, add the configuration: cmake --build build --config Release.

Build structure¶

The scene, simulation, utility and live frame and server code is built once as static libraries: egtrain_scene, egtrain_sim, egtrain_util and egtrain_live. The Qt code that several targets use is built once as well: egtrain_graphics, egtrain_widgets, egtrain_http, egtrain_update, egtrain_sceneopen (SceneOpenRequest), egtrain_openrelay (OpenRequestRelay), egtrain_telemetry, egtrain_dispatch (DispatchController, SimulationWorker and RunControl) and egtrain_diagrams. QEGTRAIN, scene_tool and the tests link them instead of listing their sources, so each file is compiled once. A test gets only the library members it references. egtrain_recovery holds RecoveryStore, RecoveryController and RecoveryPrompt. QEGTRAIN links it, and so do test_recoverystore, test_recoverycontroller and test_recoveryprompt.

Four things are still compiled more than once. The telemetry sources are built again with test hooks as egtrain_telemetry_hooks when tests are built, and as egtrain_telemetry_smoke for the application in the isolated telemetry smoke configuration, because the hooks change the layout of the telemetry classes. TelemetryConsentDialog.cpp is compiled in QEGTRAIN and in test_telemetryconsent for the same reason. update/SelfUpdater.cpp is compiled in QEGTRAIN and in test_selfupdater with EGTRAIN_UPDATE_TEST_HOOK, which adds SelfUpdater::setTestHook. app/UpdateTelemetryController.cpp is compiled in QEGTRAIN and in test_updatetelemetrycontroller, together with TelemetryConsentDialog.cpp and SelfUpdater.cpp. See Source layout.

With EGTRAIN_BUILD_TESTS=ON, QEGTRAIN also compiles the sources in EGTRAIN/QEGTRAIN/tests/e2e, the runner for the scripted GUI scenarios. At the start of main() it redirects the user settings to the folder named by QEGTRAIN_E2E_SETTINGS_DIR. After the first show of the window it starts a scenario, with blocking dialogs switched off, when the variable of that scenario is set. A build without tests, such as the three package builds, compiles none of it: in such a build the first show of the window starts no scenario and QEGTRAIN_E2E_SETTINGS_DIR redirects no settings. MainWindowTestAccess is the friend class of MainWindow that the runner calls, and of SceneDocument, whose revision a scenario sets when it replaces the scene without an edit, of SceneSession, whose scene folder and diagnostics a scenario sets, of UpdateTelemetryController, whose settings, consent and sender the telemetry smoke sets, and of RunController, whose worker, status and results a scenario reads and sets. A scenario is a member of MainWindowTestAccess defined in its own file in that folder (the legacy import smoke is LegacyImport.cpp, the scene drop smoke SceneDrop.cpp, the output folder smoke OutputFolder.cpp, the scene render smoke SceneRender.cpp, the station overlay smoke StationOverlay.cpp, the track preview smoke TrackPreview.cpp, the visual polish smoke VisualPolish.cpp, the editor smoke EditorSmoke.cpp, the creator acceptance smoke CreatorAcceptance.cpp, the crash and recovery runs Recovery.cpp). The visual polish smoke also starts from the frames of a run: renderSnapshot calls the frameRendered hook of MainWindowTestHooks after every frame, and the hook is set only when QEGTRAIN_E2E_VISUAL_POLISH is set. The editor smoke sets the passengerSource hook to the folder that Import Passengers reads in place of its dialog, and clears it afterwards. The creator acceptance smoke starts without a scene: when QEGTRAIN_E2E_CREATOR_ACCEPTANCE is set, main() opens the window through e2e::runCreatorAcceptanceMain, the first show asks no startup question (suppressStartupPrompts), and capacity analysis shows its scope dialog (askCapacityScope), which the scenario answers. The scenario opens the Time / distance window after the baseline run, runs two more scenarios, and then checks that the window still exports the baseline run and not the run that the application holds by then. A scenario keeps its state, such as whether it has begun its checks, in MainWindowTestAccess, not in the window.

Dialogs.cpp answers the dialogs that the window opens. showStartupChooser, showRunReview and UpdateTelemetryController::showPrivacySettings call the dialogShown hook of MainWindowTestHooks with the dialog just before it opens, and the first two call dialogClosed once they have read the answer. With QEGTRAIN_E2E_STARTUP_CHOOSER set, the runner records the rows and menus of the case chooser, takes the action that QEGTRAIN_E2E_CHOOSER_INTERACTION names on the row of QEGTRAIN_E2E_CHOOSER_PATH, and prints the E2E_STARTUP_CHOOSER_ lines when the chooser has closed. With QEGTRAIN_E2E_REVIEW_CANCEL set, the run review opens although dialogs are suppressed (askRunReview). The runner inspects it, cancels it with the Cancel button or, for the value escape, with the Escape key, and prints the E2E_RUN_REVIEW_ lines; QEGTRAIN_E2E_REVIEW_ENLARGED enlarges the fonts first. With QEGTRAIN_E2E_PRIVACY_DIALOG set to 1 or settings and QEGTRAIN_E2E_SETTINGS_DIR set, the privacyPreview hook gives the privacy dialog a fake context, no telemetry starts, and QEGTRAIN_E2E_SCREENSHOT names the file that receives a picture of the dialog. In the isolated telemetry smoke configuration (EGTRAIN_ISOLATED_TELEMETRY_SMOKE, described in Telemetry) TelemetrySmoke.cpp is compiled too. Its hooks telemetryStart (which gets the UpdateTelemetryController of the window), observationStep, runStarting and windowDestroyed start the telemetry in the folder that QEGTRAIN_E2E_TELEMETRY_SMOKE names, fail the steps that install the observation of a run, stop a run at the point that the mode names, and print E2E_TELEMETRY_SHUTDOWN; the actions of each mode are in runTelemetrySmoke, which tools/e2e/telemetry_smoke.py drives.

test_no_e2e_in_product runs tools/e2e/test_no_e2e_in_product.py. It fails when a source, header or form that a build without tests compiles holds QEGTRAIN_E2E_, E2E_ or failures <<. The files under tests/e2e and the telemetry smoke support are not scanned. Four files are exempt for the text that they hold on purpose: update/UpdateSettings.cpp and telemetry/TelemetryConsent.cpp test the prefix QEGTRAIN_E2E_, and app/OpenRequestRelay.cpp and app/OpenRequestRelay.h test it and name QEGTRAIN_E2E_OPEN_RELAY.

PostRun.cpp holds the autostart and the checks that follow a run. With QEGTRAIN_AUTOSTART set, the runner starts the run of the case 1.5 s after the first show. The hooks snapshotDelivered, snapshotDrawn, runResultsRefreshed, runFinished, runSettled and routeDiagramBuilt of MainWindowTestHooks call the checks of QEGTRAIN_E2E_EXPORT_DIR, QEGTRAIN_E2E_ROUTE_DIAGRAM, QEGTRAIN_E2E_SIGNAL_HEADS, QEGTRAIN_E2E_PAUSE_STEPS, QEGTRAIN_E2E_OPERATIONAL_COMPLETION, QEGTRAIN_E2E_OPERATIONAL_DISCARD, QEGTRAIN_E2E_REPLAY_WHOLE_RUN and QEGTRAIN_E2E_CLOSE_DURING_RUN, and the markers E2E_GUI_AUTOSTART_RUNNING and E2E_GUI_RUN_RESULTS. A build without tests compiles none of it, so these variables start no run and run no check there.

The hook of QEGTRAIN_E2E_EXPORT_DIR also opens the blocking-time diagram, the delay diagram and the four per-train diagrams. For the blocking-time, the delay and the speed vs distance window it writes the CSV that the window exports with all trains, with the first train and with none (<window>_window_all.csv, _one, _none). For the blocking-time, the delay and the per-train diagrams it also writes a text dump of the chart (blocking_time_series.txt, delay_diagram_series.txt, speed_distance_series.txt and so on: the axes, then every series with its properties and points). Two builds of one scene give the same files, so cmp shows whether a change moved a diagram.

The hook of QEGTRAIN_E2E_ROUTE_DIAGRAM builds the train paths and the timetable graph with each route that trains run on as reference. For each of them it writes the text dump of the chart and the CSV of the window with all trains (train_path_graph_route<N>_series.txt, train_path_graph_route<N>.csv, and timetable_graph_route<N> likewise, with N the index of the route in the run).

Warnings¶

The build passes -Wall -Wextra (/W4 with MSVC) to the strict targets and to egtrain_dispatch. The cache option EGTRAIN_WARNINGS_AS_ERRORS is OFF by default. With -DEGTRAIN_WARNINGS_AS_ERRORS=ON a warning in a strict target fails the build:

cmake -S . -B build -DEGTRAIN_BUILD_TESTS=ON -DEGTRAIN_WARNINGS_AS_ERRORS=ON

The pull request checks use the option on all three platforms. The targets are listed in Coding guidelines.

Run a local build¶

From EGTRAIN/QEGTRAIN, use the executable produced by the selected generator:

# macOS
../../build/QEGTRAIN.app/Contents/MacOS/QEGTRAIN

# Windows PowerShell, multi-config generator
..\..\build\Release\QEGTRAIN.exe

# Linux
../../build/QEGTRAIN

A single-config Windows build may place the executable at ..\..\build\QEGTRAIN.exe. These are local build paths; downloaded release packages are documented in Installing EGTRAIN.

Runtime output defaults to <QStandardPaths::AppDataLocation>/Output/<scene>. It does not always use a repository Output/ directory. Set QEGTRAIN_OUTPUT_DIR to override the base directory; EGTRAIN then writes <override>/Output/<scene>.

Unit Tests¶

ctest --test-dir build --output-on-failure

With a multi-config generator such as Visual Studio, build and test the same configuration, for example cmake --build build --config Release and ctest --test-dir build -C Release. ctest -N lists the tests registered on the current platform.

Tests can run side by side: ctest --test-dir build -j N --output-on-failure. A test that starts the application keeps its user settings in a folder of its own, most of them below build/settings, so none of them reads or changes the settings of the user. CI runs ctest --parallel with the number of cores of the runner.

Scene compatibility tests cover manifest probing, independent schema/bundle classification, hostile newer bundles, and transactional test-only migration chains. They also cover the validation of an upgraded copy, a source scene that cannot be loaded, and a refused write. The refused-write case skips itself when a new directory can still be created in a read-only one, for example for a process with root rights. The production migration registry is empty on purpose: every scene written so far has version number 1, so there is no number to convert from. test_sceneversions reads the scenes in tests/fixtures/scene-versions. They are byte copies of scenes written by older builds, listed with their origin in manifest.json, and a fixture is never edited or saved again. For each one the test checks the class, the version numbers, loading, validation, the sizes of the loaded model, and that a copy upgrade is refused and leaves the fixture unchanged. The stored draft-layout scene is pinned as unsupported with the diagnostic that names the draft layout, and as not runnable. A rejected schema number is checked on a copy that the test makes, with the diagnostic that names it. A guard fails when a version constant is raised without a fixture of the previous number and either a migration for it or manifest entries that list every fixture of that number as unsupported.

A release that raises kCurrentSceneSchemaVersion or kCurrentSceneBundleVersion changes the scene format. After it is published, download one of its bundles from the release and copy it unchanged into tests/fixtures/scene-versions. Add an entry to manifest.json with the release in origin and the other keys of an existing entry (counts come from the loaded model). If the bundle is meant to run, add a test_scene_version_run_* test next to the existing ones in the root CMakeLists.txt, with the same TIMEOUT, and add its name to the integration list of egtrain_label_tests. The next raise of a number then finds a fixture of the current one.

scene_tool has no migrate command; it offers import, pack, unpack, export and validate. The Compatibility boundary says which scenes are supported.

The native builders and TrackPreview tests operate on an in-memory canonical SceneModel; the builders perform no input-file reads. GUI and headless runs both enter the same DispatchController::prepareScene path.

test_scenehistory checks SceneHistory without Qt: the order of Undo and Redo, the Redo branch that an edit discards, the saved position across undo, redo, edits and dropped snapshots, both limits with injected values, the labels, and the replacement of the scene by reset. It also removes each part of a rich scene in turn and checks that estimateSceneModelBytes drops, so a container that the estimate leaves out fails the test. For each committed scene it records 101 edits with the default limits and checks that the step count and the estimate stay within them.

test_scenedocument checks SceneDocument without a window: the signals, the revision and the unsaved state of replace, markChanged, markSaved and restore, and that assignAuthoredScene takes every authored part of a snapshot and keeps the loaded data, the source files and the version that saved the scene.

Each panel of editors/ has a test, test_editor_<panel>, such as test_editor_casesettings and test_editor_service (labels unit and gui, run with the offscreen platform). It puts the panel over a SceneDocument and over a UserPrompts that records its questions, so that no dialog opens, and works the widgets of the panel. It checks that a refresh lists the model and, as far as the panel has them, that an edit, an addition and a deletion change the model and mark the document once, that a refused or cancelled edit changes nothing, and that a rename keeps what refers to the entity. The infrastructure facets have one test for each file of facets: test_editor_infrastructure_topology, test_editor_infrastructure_blocks, test_editor_infrastructure_stations and test_editor_infrastructure_signals. test_editor_infrastructure checks the panel itself with facets of its own, including where its buttons and the sections of a route are placed. test_infrastructureguidance checks the sentence above the table for each of the thirteen facets, with and without entities and a scene.

test_recoverystore checks RecoveryStore in one process: the layout of an instance folder, writing and replacing a copy, a failed write that keeps the previous copy, the copies that an ended instance left behind, the choice of the newest complete bundle, unusable and unknown records, pruning, the limit of 20 kept instances, clear and close, adopt and discard, and the comparison of a source with its copy. A case that needs POSIX permissions skips itself on Windows and when the process may write into a read-only folder anyway. test_recoverystore_process (label integration) starts the test program again as a child that writes a copy and holds its lock, and as a child that ends without a clean close. The parent checks that a scan lists nothing for the running child, that it lists the copy once the child was killed or has ended, and that a new store can adopt that copy.

test_recoverycontroller runs RecoveryController with an event loop and an interval of 10 ms, which it sets in QEGTRAIN_RECOVERY_INTERVAL_MS; the default is 30 s. It checks the interval variable, that the edits of one interval give one write of the newest scene, that later edits do not move the timer, that a revision on disk is not written again, that edits during a write give one more write, that a save, a replacement or a return to the clean state leaves no copy when a write is running or waiting, that shutdown waits for the write and removes the instance folder, that the destructor leaves the copy, that a failed write or removal is reported once per run, and the scan, adopt and discard calls, including an adoption that fails after the removal of the previous copy was handed to the worker. The test holds the worker thread at two points of a job with a hook that the constructor takes, so the cases for a write in flight do not depend on how fast the write is. The checks that nothing happens wait a fixed 100 to 150 ms, and the timer case uses an interval of 2 s. The removal case changes the permissions of a folder and is skipped where that has no effect, as for a superuser and on Windows.

test_recoveryprompt (labels unit and gui) shows RecoveryPrompt on the offscreen platform and never calls exec(). It checks one row for each copy with its name, time and source, the note for a changed, missing, newer or unknown original and for a copy that this version cannot open, the default button of each row, the results of Recover, Decide Later, Escape, closing the window and Enter, that Discard needs a second click that names the case, the line about copies removed over the limit, and that a long name or path, many rows and a large font keep the dialog inside the available area with the buttons in reach.

test_openrequestrelay (label integration) checks OpenRequestRelay, which hands a file from a second launch to the running window. The test program is the running instance, and it starts itself again as the second process. It checks that a path with spaces and non-ASCII characters arrives once and unchanged and that the second process ends with 0, that a request for another application folder is refused, that a name held by a running instance is not taken over while a name left behind by a killed one is, that a request in two parts is accepted and bytes that are no request, or more than a request holds, are dropped, that only the newest postponed request comes back, and the rule for the test variables. The relay also takes the QFileOpenEvent that macOS sends when Finder opens a file with the program. The test sends such events to the application: the path of a file with spaces and non-ASCII characters is reported once and unchanged from the event loop, an event for a URL that is no local file is left alone, of two events in one turn the newest remains, and a request that nothing is connected to yet waits for a receiver. On macOS and Linux the socket files lie in a folder directly below /tmp, because a socket path is limited to about 100 characters. test_startup_launch_contract adds the window: a window started with a file, and one with the chooser open, each open a file that a launch without test variables hands to them, the window leaves a handed file that does not load out of the recent cases, and a scripted launch with a file keeps its own window. A run with any QEGTRAIN_E2E_ variable neither listens nor hands over a file, unless QEGTRAIN_E2E_OPEN_RELAY is set as well, which the contract sets for the window only. The test hook QEGTRAIN_E2E_OPEN_REQUEST names a file that the run hands to the application as a QFileOpenEvent, as the first show of the window begins (QEGTRAIN_E2E_OPEN_REQUEST_AT=launch, the default), 50 ms later while the program still starts (startup), from inside the open case chooser (chooser) or one second later (running). It prints whether the chooser is open when the event comes, and the chooser and the status line three seconds after it. The contract uses it to show that a window started without a file opens a file from an open event, with spaces or non-ASCII characters in its name, without the chooser, that a running window opens one too, that an event from inside the open chooser closes the chooser and opens the file, and that a malformed file is reported and stays out of the recent cases. On macOS the startup callback waits 300 ms before it opens the chooser, so that the event of a launch from Finder is seen first; the startup moment checks that no chooser opens then. A real double-click in Finder is not part of it.

Test labels¶

Every test has exactly one of unit or integration. Configuration fails when a test has neither or both.

  • unit: runs in-process or is a static check. It starts no QEGTRAIN, scene_tool, update helper, or socket server.

  • integration: starts or inspects a built program (QEGTRAIN, scene_tool, egtrain_update_helper, or a test that starts its own executable as a child) or talks to a loopback server.

  • gui: needs a Qt platform plugin (the tests use offscreen) or launches QEGTRAIN in GUI mode. Combine it with either of the labels above.

  • slow: takes more than 20 seconds on a development machine.

  • network: sends a request to a server on the internet. It is registered only with -DEGTRAIN_NETWORK_TESTS=ON, so no other test run needs the internet. Combine it with integration. See HTTPS update check.

To add a test and register its labels, see Coding guidelines.

ctest --test-dir build -L unit --output-on-failure
ctest --test-dir build -L unit -LE gui --output-on-failure
ctest --test-dir build -L unit -LE slow --output-on-failure
ctest --test-dir build -L integration --output-on-failure
ctest --test-dir build -LE slow --output-on-failure
ctest --test-dir build -L gui --output-on-failure

On Windows add -C Release to each command.

Scene tests use CTest labels too:

ctest --test-dir build -L scene-v1 --output-on-failure
ctest --test-dir build -L legacy-compat --output-on-failure
ctest --test-dir build -LE legacy-compat --output-on-failure

scene-v1 covers the canonical scene model. legacy-compat covers only the explicit importer/exporter boundary; normal simulation is not in that label. scene-v2 covers .egscene container round-trips, hostile-archive checks and the released scene fixtures.

HTTPS update check¶

test_updatetransport_https (labels integration and network) makes one real GET of https://api.github.com/repos/Ancientkingg/EGTRAIN/releases?per_page=1 through createHttpTransport and reads the answer with parseLatestStableRelease. On Windows that is the WinHTTP transport, so the test shows that a machine without a Qt TLS library can make the request of the update check. It is registered only when the configuration asks for it:

cmake -S . -B build -DEGTRAIN_BUILD_TESTS=ON -DEGTRAIN_NETWORK_TESTS=ON
ctest --test-dir build -L network --output-on-failure

On Windows add -C Release to the ctest command. Its output starts with PASS, SKIP or FAIL. An answer with an HTTP status has reached the server, so the TLS handshake and the certificate check worked, and the test tells the cases apart by what came back:

Result

Cause

PASS, exit code 0

The release list arrived and was read. A list whose newest release is a prerelease also passes.

SKIP, exit code 77

GitHub answered with HTTP 403 or 429 (its rate limit) or with 5xx (an outage). CTest shows the test as skipped.

FAIL, exit code 1

No HTTP response arrived: the name lookup, the connection, the TLS handshake or the certificate check failed, or 45 s passed. Also any other HTTP status, whose text says that it is not a TLS failure, and a body that is not a release list.

The anonymous GitHub API allows 60 requests an hour for one address, and a run makes one request. The program reads no rate-limit header, so every 403 counts as a rate limit.

test_updatetransport_https_cases runs the same program against a server on 127.0.0.1 that gives each kind of answer, and runs in every configuration without the internet.

The Windows leg of the CMake workflow configures with -DEGTRAIN_NETWORK_TESTS=ON, leaves the network tests out of the Test step with -LE network, and runs them in the step Check HTTPS (Windows). The Windows package job builds the program with the package and runs it in the step Check HTTPS from the package. That step copies the program into the copy of the package that the start check used and runs it with only the Windows directories on PATH, so it loads the Qt files of the package, as a machine without a developer setup would.

Windows GUI tests¶

The offscreen Qt platform has no fonts of its own on Windows. CTest sets QT_QPA_FONTDIR to the system font directory for every test with the gui label. Set it yourself when you start a GUI test or QEGTRAIN with QT_QPA_PLATFORM=offscreen by hand.

Qt 5.15 crashes when a QMessageBox is shown on the offscreen platform on Windows: QMessageBox::showEvent asks for a native window handle through an interface that this platform does not have. test_scene_drop needs the unsaved-changes prompt and test_completedrun closes a message box if a refusal of the capacity dialog opens one, so CTest runs both with QT_QPA_PLATFORM=windows there. A scripted run that reaches any other message box on the offscreen platform fails the same way on Windows.

Windows headless runs¶

QEGTRAIN is a GUI-subsystem program on Windows (WIN32_EXECUTABLE). With -g 0 it opens no window and reports only through redirected output handles and its exit code (0 on success, 1 for bad arguments or scene errors). Started from a terminal it prints nothing, and & QEGTRAIN.exe in PowerShell does not wait for it. Start it from a program that creates the process and reads the pipes, such as tools/e2e/headless_scene_smoke.py, or from PowerShell with Start-Process; the two output files must differ:

$dir = Resolve-Path .\build\Release
$p = Start-Process -Wait -PassThru -NoNewWindow -WorkingDirectory $dir `
  -FilePath "$dir\QEGTRAIN.exe" `
  -ArgumentList '--scene','Scenes/Paimpol','-h','300','-g','0','-pax','0' `
  -RedirectStandardOutput "$PWD\out.txt" -RedirectStandardError "$PWD\err.txt"
$p.ExitCode

The working directory is the one that holds QEGTRAIN.exe, where the build copies Scenes/. Set QEGTRAIN_OUTPUT_DIR to keep the output out of the profile directory.

Windows package start¶

After the tests, the Windows CI leg assembles the files of the release package in a temporary directory: QEGTRAIN.exe, the vcpkg DLLs, the Qt DLLs and plugins that windeployqt adds, and the scenes, without the Visual C++ runtime DLLs (the runner has the runtime, and the package job checks the imports). It then runs tools/release/package_start_smoke.py on that directory. The script removes the Qt, vcpkg and library path variables from the environment and leaves only the Windows directories on PATH, so a DLL or plugin that is missing from the package fails the launch. It starts the packaged program in this order:

  1. Headless on Paimpol to the end of a 120 s run.

  2. With a window in startup timing mode, where the program opens the scene, prepares a run, paints it and exits.

A release package has no test hooks, so the script makes two more launches only with --exports, for a package assembled from a build with EGTRAIN_BUILD_TESTS=ON:

  1. The CSV export.

  2. The PNG export.

The Windows CI leg passes --exports, because it assembles the package from its build with tests. The package workflows build release packages and do not.

The two export launches run Paimpol with a window and a horizon of 8000 s, with the autostart hook and one export hook of the application each: QEGTRAIN_E2E_EXPORT_DIR for the CSV files and QEGTRAIN_E2E_ROUTE_DIAGRAM for the PNG files. The hook writes into a new temporary directory and then exits the application, so each export is a launch of its own. The script requires the marker that the application prints (E2E_CSV_EXPORT_OK, E2E_ROUTE_DIAGRAM_OK) and the files that the hook names: the CSV files trajectory.csv, timetable.csv and run_summary.csv, each not empty, with a header line and a data line, and the PNG files timetable_graph.png, train_path_graph.png and route_reference_chooser.png, each with a PNG signature. It does not check the values in the files or how the images look.

Before the launches the script fails when a file of the package is an OpenMP runtime library or names one (vcomp140.dll on Windows): the package ships none.

The assembly uses the same windeployqt options as the Windows package job (--no-opengl-sw, --no-angle, --no-system-d3d-compiler, --no-virtualkeyboard and --no-quick-import besides --release, --no-translations and --no-compiler-runtime), and test_ci_workflow keeps the two command lines equal. The Windows package keeps the bearer plugin and the image format plugins. It holds no vc_redist.x64.exe: see Windows package runtime.

Windows package runtime¶

The installer installs for the current user and cannot run the Visual C++ redistributable, so the Windows package carries the runtime DLLs that its program files import (for example VCRUNTIME140.dll, VCRUNTIME140_1.dll and MSVCP140.dll) next to QEGTRAIN.exe (app-local deployment). Their redistribution follows Microsoft’s Visual C++ redistributable terms; the package holds no notice file of its own for them. The Universal CRT (api-ms-win-crt-*, ucrtbase.dll) is part of Windows 10 and 11 and is not copied. The step Copy the Visual C++ runtime of the Windows package job finds the x64 folder Microsoft.VC14*.CRT below VCToolsRedistDir and copies the DLLs that tools/release/pe_imports.py --missing lists for the package. The step Check the DLL imports of the package runs tools/release/pe_imports.py dist/QEGTRAIN, and the Finalize Windows job runs it on the extracted portable archive. The script reads the import tables and the delay-load import tables of every .exe and .dll below the directory and exits 1 when one names a DLL that the package lacks and that is not in its list of Windows system DLLs (SYSTEM_DLLS and the api-ms-win- and ext-ms-win- prefixes). A new system DLL that the program starts to import goes into that list. GitHub’s Windows runners have the runtime installed system-wide, so starting the package cannot show a missing runtime DLL; the import check does. test_pe_imports tests the reader on PE files that it builds. Run the check by hand on an extracted package with python3 tools/release/pe_imports.py <folder>.

macOS package start¶

The macOS package job removes the virtual keyboard input plugin with the Quick and QML frameworks that it links, and the WebP and TIFF image plugins with their libraries, from the app after macdeployqt and before the signature. In the same place tools/release/macos_build_paths.py fix deletes the run paths under /opt/homebrew and /usr/local and gives a file whose install name is under one of them the name @loader_path/NAME; macos_build_paths.py check then fails on any such path in the otool -L, -D or -l output of a Mach-O file of the app (test_macos_build_paths). The CMake workflow assembles no macOS package. The package job runs tools/release/package_start_smoke.py on a copy of the app (step Start the package).

For a package with an app bundle, the script first reads the load commands of every Mach-O file with otool -l. It fails unless every dependency is a system library (under /System/Library/ or /usr/lib/) or a file inside the app, and every library inside the app is loaded by some file. The search starts at the files in Contents/MacOS and Contents/PlugIns, which no load command names: the system starts a program, and Qt finds a plugin by its directory. The script then starts the app as for Windows: the headless run and the window start. Only the launch with a window loads the cocoa platform plugin of the bundle.

The macOS package keeps QtDBus and QtPrintSupport, which the cocoa platform plugin loads, the print support and bearer plugins, and the image format plugins other than WebP and TIFF.

Linux package start¶

The Linux package job extracts the AppImage that it built into a directory under the runner temporary directory, so the file that is uploaded stays as built. The job installs xvfb and xauth with the build tools. In step Start the package it lists the plugin files of the extracted image in its log and runs tools/release/package_start_smoke.py on the directory with xvfb-run, which gives the program a virtual X display. The script starts the directory through its AppRun, as the AppImage runtime does after it has mounted the image, and makes the same launches as for Windows: the headless run and the window start.

Before the launches the script runs ldd on every ELF file below usr/bin and usr/plugins. It fails unless each Qt 5 and ZeroMQ library that such a file loads is a file of the extracted image, and it fails when ldd lists no such library at all. The runner has the Qt 5 packages that the build needs, so an image that lacks a Qt library would otherwise still start there with the library of the runner. The plugins are read as well as the programs, because the platform plugin loads Qt libraries that the program does not. The job sets no platform plugin variable, and the script removes every Qt variable and LD_LIBRARY_PATH from the environment of the launches, so the image starts with the platform plugin that it holds.

Windows image size¶

Windows maps an EXE as one image whose size is SizeOfImage in the PE header, and does not start an image near 2 GiB (it reports that the file is not a valid Win32 application). test_windows_image_size fails when SizeOfImage of QEGTRAIN.exe is above EGTRAIN_MAX_PE_IMAGE_BYTES (default 100000000), or when the executable is not x64 and a Windows-subsystem program. A Release build has an image of about 6 MB and a Debug build of about 18 MB, so the limit is reached only when fixed-size static storage comes back. Set the variable at configure time to change the limit. To check a build by hand:

python tools/release/pe_image_size.py build/Release/QEGTRAIN.exe --max-bytes 100000000

The first output line shows the measured size. The CI workflow prints the same line in the job summary.

The same header holds the stack reserve. QEGTRAIN.exe is linked with 8 MiB, the size the main thread has on macOS and Linux, and test_windows_image_size checks that value. The other executables keep the linker default of 1 MiB, which test_windows_default_stack checks on scene_tool.exe. On Windows the reserve of an executable is also the stack size of every thread that is started without one, so it is set for the application only. Measured on macOS: each of the six committed scenes runs headless with the stack of the main thread limited to 128 KB, and none starts with 64 KB. To repeat it, run ulimit -s 128 in a shell and then the application with --scene <scene folder> -g 0.

Characterization tests¶

The characterization tests pin what the simulation core does today, so that refactors of movement, signalling and global state show up as a reviewable diff. They drive the real DispatchController in the test process on the small scene EGTRAIN/QEGTRAIN/tests/fixtures/scenes/line (“Characterization Line”): one track of 16 km in eight blocks of 2 km, three stations, seven services and twelve scenarios (baseline, signal-failure-forward, signal-failure-reverse, signal-failure-adjacent, signal-failure-staggered, signal-failure-last, signal-failure-first, signal-failure-entered, signal-failure-late, signal-failure-retarget, entrance-delay-f2, breakdown-f1). The stub cases add the routes routeStubIn and routeStubOut and the services U1 and D1 to the scene in the test, because a route with 4-B0 or 5-B0 in the fixture would add a movement authority to the cases with a signal failure on those sections.

The passenger cases add station P, services Q1 to Q3 and passengers in the test. Transfer cases also add Platform_4 on B: its numeric label reaches the walking time calculation, while B.platform.1 reads as 0. cmake --build build --target test_characterization test_crossover_chain test_signalling_aspects
ctest --test-dir build -L characterization --output-on-failure

characterization_repeatable runs several cases in one process and then the first one again. The two runs of that case must be identical, with no tolerance. It fails when state from an earlier run leaks into a later one. The same executable can run any scene directories back to back:

build/EGTRAIN/QEGTRAIN/tests/characterization/test_characterization \
    --repeat EGTRAIN/QEGTRAIN/Scenes/Paimpol EGTRAIN/QEGTRAIN/Scenes/Assignment_Gvc_Gdg_Ut \
    EGTRAIN/QEGTRAIN/Scenes/Paimpol

A step is a scene directory, optionally followed by # and a case name. Without a case name the scene runs as committed.

Three more entries run committed scenes this way: characterization_repeat_paimpol (Paimpol twice, then Assignment, then Paimpol again), characterization_repeat_milano_paimpol (Milano-Brescia and Paimpol, alternating) and characterization_repeat_netherlands (Netherlands, Paimpol, Netherlands, labelled slow). They fail when a run leaves state behind that changes a later run of the same scene, which is what a change to the arrays of the run can cause.

These entries compare the observation of each run: what the test reads from memory, and the two station statistics files. The other files of a run are not read. --repeat-files runs the steps in the same way, but every run writes its files into a folder of its own (run-01, run-02 and so on, in a temporary folder), and after the last run every distinct step runs once more in a fresh process of the same executable, with the same working directory and environment. Every file of every in-process run must then be equal, byte for byte, to the file of the fresh run of its step, and both must hold the same set of files. The files are the ones a headless run of the application writes with --detailed-trajectories, including TrainServicePathDiagram.txt, which the test writes after the run as the application does. TrainTrajectories/Computing_Times.txt is the only file whose content is not compared. It has to exist, but it holds wall-clock timings and the computation time accumulated over the process, so it differs from run to run. As with --repeat, a step has to appear twice. A difference is reported with the run, the step, the file and the first differing line, and the folders of a failed test are kept; the message names them. The fresh run is --single STEP --output-dir DIR, which can also be used by hand. Use a new or empty folder, because a run replaces only the files it writes.

build/EGTRAIN/QEGTRAIN/tests/characterization/test_characterization \
    --repeat-files EGTRAIN/QEGTRAIN/Scenes/Paimpol EGTRAIN/QEGTRAIN/Scenes/Paimpol

Three entries run this way. characterization_repeat_files_paimpol (labelled slow) and characterization_repeat_files_milano_paimpol run the sequences of characterization_repeat_paimpol and characterization_repeat_milano_paimpol. characterization_repeat_files_fixture runs sf-forward-level-3 twice, single-track-level-4, and sf-forward-level-3 again on the line fixture, which gives an incident and a single-track restriction that no committed scene has. They fail when a run in a process writes a file that differs from the file of a fresh process, which is what state left behind by an earlier run can cause in a file that the entries above never read.

characterization_aspects_dutch (labelled slow) runs Netherlands and Assignment once each with --aspects and fails unless at least one route section leaves the clear code 270 and returns to it during the run.

test_crossover_chain is a separate executable, because the harness above is tied to the line fixture (its length, its block size and the station at 8 km). It runs the scene tests/fixtures/scenes/crossovers: a chain of five tracks with two crossovers that follow each other directly, so that the second half of the first crossover and the first half of the second one share one long block. The rolling stock and the timetable are copied from the line fixture. Platform B lies inside the second crossover, and F1 reaches it long before its planned departure, so F1 stands in the crossover while F2 arrives. The geometry is synthetic. For each of the levels 0, 1, 2 and 5, one CTest entry (characterization_crossover_chain_level_0, -1, -2, -5) sets a network-wide area of that level and runs train F1 alone, train R1 alone in the opposite direction, and F1 with F2 behind it. A train alone has to reach its last platform and stand only at platforms. The follower has to reach it too, stay behind the rear of F1, and not enter the second crossover while F1 is in it. At levels 0, 1 and 2 it also has to wait in the second half of the first crossover meanwhile; at level 5 it waits further back, in front of the first crossover, and that is not checked. The levels 3 and 4 are not run, because a train alone does not stop in front of the second crossover there. The test reads no golden file. Each level also runs R1 on a route marked reversed with its sections in reverse order, with the same expectations, and refuses F1 on a route marked reversed with its sections in forward order with scene.route.direction.

test_signalling_aspects is a third executable, because it needs no scene and no Qt. It builds routes of up to seven sections by hand in the route list of the run and calls the release and the activation of the mixed signalling (releaseMixedSignallingSystem and activateMixedSignallingSystem, in the order of a step) and the release of the last section (relLastSectionMixedSignalling). After a step it writes the code, state, signal speed limit, speed in braking and exit speed of every section: one line per case, with the group, the parameters, a | and one token code:state:signal:braking:exit per section. The header of the golden file tests/characterization/expected/signalling-aspects.txt explains the fields. The groups are uniform levels, two levels with a border, three or more levels, sweeps of a moving train that carry the state from step to step, the release functions, other signal speeds and a held single-track zone. The cases are in the file, and the comparison is exact text, without a tolerance. The speed limits of the sections are numbers of the test, not railway data. The test also checks, without the golden file, the aspects of one step for every level, the release of one connected section on two routes of different lengths, the level mask of a route, and that a step leaves the lists of occupied and connected sections as they were. A change of the aspect routines that is not meant to change behaviour has to leave the file as it is. The file has no # case: line and no # known-wrong: line, because it is not a case of the table. It is recorded with EGTRAIN_UPDATE_EXPECTATIONS=1, like the others. The command in “Changing an expectation deliberately” that runs every characterization test records it too; this command records it alone:

EGTRAIN_UPDATE_EXPECTATIONS=1 build/EGTRAIN/QEGTRAIN/tests/characterization/test_signalling_aspects \
    --expect EGTRAIN/QEGTRAIN/tests/characterization/expected/signalling-aspects.txt

The test does not call diverging switches, double switches, station boundaries, signal failures or the authorities of levels 3 and 4. Its CTest entry is characterization_signalling_aspects, labelled characterization and unit.

Reading a golden file¶

Golden files are in tests/characterization/expected/<case>.txt. Lines starting with # are comments. The header names the case and the run. Every other line is one fact: some key words, then name=value fields.

  • train <id> sample: time t (s), route position x (m) and speed v (m/s), every 60 s from the first to the last step the train is in the network.

  • train <id> stop: a stretch of at least 5 s below 0.001 m/s, with its first and last step, position and dwell (last minus first step).

  • train <id> braking: the last step at the speed before a stop that is followed by a continuous speed decrease down to that stop.

  • separation <lead>><follower>: the smallest distance between the rear of the leading train and the head of the one behind it, and when. Negative means overlap.

  • aspect <route> <section>: the signal aspect code of the section as step:code at every change, starting at step 0 (270 clear, 180, 75, 0 stop, 751 BACC).

  • result, run_result, network: timetable and run results as the application reports them. n/a means the value is not available.

  • blocktime: the blocking-time records of a train.

  • capacity_pair <leader> <follower> and capacity_resource <section>: what analyzeCapacity and analyzeAreaCapacity report for the two trains of a case, with all sections of their route as the area and a period of 3600 s, the default of the capacity dialog. Only the cases follow, sf-forward, sf-reverse, sf-adjacent, sf-staggered, sf-last and sf-first at the levels 0 and 2 have them, and only when both trains have complete blocking times; F2 is still in 7-B0 when sf-adjacent-level-0 ends, so that case has none. The pair line gives min_headway (s) with the sections that govern it, cycle (s) and cycle_pct (percent of the period) from the first train to the second after compression, whether the compressed trains overlap (conflict_free), and the sections where they touch (critical). Each resource line gives the number of trains and occupations of a section, the sum of the occupation times (occupation, s), their union (union, s), occupation_pct, and governing=1 for the section with the largest sum. The values cover these two trains only, not the capacity of the line.

  • incident, boundary, authority: the incident definition, and for the steps just before and after its start and end, how many signal-failure authorities exist and which sections are blocked.

  • stats: the rows of TrainTrajectories/Stats_Stations.txt, which holds six significant digits. An early arrival counts there as a delay of 0 in the total and in N_StopTrains. The average and deviation cover the delayed trains only.

  • signed_stats: the same rows of TrainTrajectories/Pos&Neg_Stats_Stations.txt, where early arrivals are negative delays.

  • delay_summary <arrival|departure> <station|network> and delay_input <train>: what summarizeDelays reports for the timetable results of the run and the entrance delay of each train, with the thresholds 0, 60, 180 and 300 s (a call is later only when it is strictly later). A row counts its calls by status and by early, on time and late, and gives sum, mean, minimum and maximum over the calls that have a delay; n/a means no call has one, never 0. Only the cases entrance-delay-f2-level-0 and breakdown-f1-level-0 have them. A delay-pair-<incident case>.txt file comes from test_characterization --pair <baseline case> <incident case>, which runs both cases in one process. It holds the same lines for both runs, with baseline or incident after the key, and the lines of compareAgainstBaseline: delay_compare status, one delay_compare diagnostic for every reason a baseline does not fit, a delay_compare occurrence line per train (entrance delay, direct evidence, final call, additional delay and secondary), a delay_compare call line per call and a delay_compare total. Its CTest entry is characterization_delay_pair_<incident case>.

  • pax <id> state: changes in network membership, status, active journey and trip, waiting station and platform, awaited and boarded trains, and arrival station.

  • gui_platform <station> <platform>: changes in the ordered passenger IDs sent to the window; - means empty.

  • gui_passenger <id>: changes in status, waiting platform, next train and next destination sent to the window.

  • onboard <train>: changes in onboard count and capacity sent to the window.

  • journey <passenger> <journey> and trip <passenger> <trip>: final start and completion flags, actual times and arrival delay, plus walking and waiting times for journeys. Passenger times are absolute seconds of the day; trace t values are steps of the run.

  • file PassengerStatus.txt and file JourneyDelays.txt: every line of the two passenger files, as whitespace separated tokens.

Passenger traces store the first snapshot and print only later changes, in step order. Passenger windows have equal ends, so no golden depends on the seed.

Transfers to a platform with another label never complete: the passenger stays on the arrival platform. Waiting time is accumulated for the first journey only. With PAX_GUI off the persistent platform lists stay empty. The snapshot part for passengers who just left never matches when the base time is at or above the horizon. A station with platforms on two nodes of one route has one timetable point per node; result rows and statistics for a stop at that station read the first point. See Delay analysis.

Both station statistics files take the arrival of a stop from its timetable point, the arrival that TimetablePoints.txt, the timetable results, the diagrams and the CSV export report, so a result line and a station row show the same delay. A train that did not reach a stop, and a stop without a planned arrival, have no delay and are counted in neither file. A stop with no timetable point keeps the arrival recorded during the run. A station row without such a train holds -1 in the average, deviation, maximum, cumulative and percentage columns and 0 in Total_Delay and the train counts. The Final_Station row is the same statistic over the last stop of each train whose last stop is counted; when no last stop is counted it holds the values of a row without a counted train. The first station of the network has no row and is not in TOTALS; its calls can still be the last stop of a train and so enter Final_Station. See Delay analysis.

Integers and strings must match exactly. Floats match within an absolute tolerance of 1e-4 and a relative tolerance of 1e-9, and the statistics rows within 1e-5 relative. A failure prints the first 20 differing lines with the expected and the actual line, and writes the actual output to <case>.actual.txt in the test’s build directory.

Each run also checks facts that do not come from the golden file, so a re-recorded golden cannot hide them: speed never above the 36.11 m/s limit, no backward movement, acceleration and braking within what the rolling stock can do, no faster run to station B than the top speed allows (in a stub case only for a train that starts before B), planned dwell and departure times kept, stops only at a platform, a block boundary or behind another train, no overlap of two trains, and in every station row of stats and signed_stats a Total_Delay and an N_StopTrains that equal the sum and the number of the arrival delays of its result lines (only the late ones in the sum for stats). In a single-track-* case S1 and R1 are never inside the restricted section at the same time. In a stub case both trains reach their last stop and are never inside the stub together. The terminating running approaches also must all reach their last stop, and every running case checks opposing zone overlap at every shared step. A case without a signalling area is not checked for overlap or for the single-track section: a scene without a signalling level does not separate trains, and validation warns about it (scene.signalling.level.missing, scene.single_track.no_effect). The -level-none goldens therefore show trains at one position.

The signal states that the simulation hands to the window are checked at every step of every case against the section codes of all routes. There must be one entry per section and direction. Its code is the most restrictive code of the route copies of the section (0, 751, 75, 180, 270 in that order). Its level is the signalling level of the section, or none. Its failed flag is set exactly from the start to the end of a signal failure.

Changing an expectation deliberately¶

Run the case with the update switch, then review the diff before committing:

EGTRAIN_UPDATE_EXPECTATIONS=1 ctest --test-dir build -L characterization
git diff EGTRAIN/QEGTRAIN/tests/characterization/expected

To run one case directly, call the executable:

EGTRAIN_UPDATE_EXPECTATIONS=1 build/EGTRAIN/QEGTRAIN/tests/characterization/test_characterization \
    --fixture EGTRAIN/QEGTRAIN/tests/fixtures/scenes/line \
    --expect EGTRAIN/QEGTRAIN/tests/characterization/expected --case follow-level-3

The switch rewrites the golden file and passes. It is refused when the CI environment variable is set, and it writes nothing when a check above fails. Read the whole diff and check that every changed number is a consequence of the change you made and still physically plausible. Commit the new golden file in the same commit as the behaviour change and give the reason in the commit message. Do not edit the scene fixture to make a case pass. Changing it changes every golden file, so add a service or scenario instead.

Known-wrong behaviour¶

Behaviour that is known to be wrong can be pinned and marked. The golden file still pins it, so a refactor cannot change it unnoticed. The golden header carries # known-wrong: #<issue> <reason> and the case table carries the same text. The test fails when the two differ and prints KNOWN-WRONG #<issue> on every run. A marked case is exempt from the checks on stops, separation and timetable. The change that fixes the bug updates the golden file and removes the marker in one commit. The markers are in the kKnownWrong table of test_characterization.cpp. List the marked cases with:

grep -rn "known-wrong: #" EGTRAIN/QEGTRAIN/tests/characterization/expected

No case carries a marker. The table is empty, every golden header says # known-wrong: none, the grep lists nothing and the checks apply to every case.

Simulation Smoke Test¶

tools/e2e/headless_smoke.py

The smoke test runs Netherlands (-n 1), Paimpol (-n 2), Copenhagen (-n 3), Brescia (-n 4), Assignment (-n 5), and Amsterdam_Hilversum_Student, which has no -n number and is case 7 of the script. It checks clean native execution and the available trajectory/station evidence. For every scene it also requires that no train moves farther in one step than the highest maximum speed of the scene’s rolling stock allows, and that no train steps against the direction of its route by more than 0.1 m. The direction comes from the flag in the train’s row in TrainTrajectories/TrainServicePathDiagram.txt. The script starts every run with --detailed-trajectories, because those checks read TEMP/Traj_Train_*.txt. Every scene run must also write section records to BlockingTimes.txt. CTest runs the position checks in test_headless_smoke_decode on trajectory and timetable files that the test writes.

The script runs the application that QEGTRAIN_APP names. Without that variable it uses the build folder of the system: build/QEGTRAIN.app/Contents/MacOS/QEGTRAIN on macOS, build/QEGTRAIN on Linux, and build/QEGTRAIN.exe or build/Release/QEGTRAIN.exe on Windows. If none exists it stops and names the paths it tried. CTest runs each case as its own test, test_headless_smoke_case_1 to test_headless_smoke_case_7, so that the cases run side by side.

For Amsterdam_Hilversum_Student the script also checks that every occurrence of its service reaches Hilversum, one after the other, and that the five files infrastructure.json, rolling_stock.json, scenarios.json, stations.json and views.json equal the Netherlands files. Its signalling.json must equal the Netherlands file apart from the signalling areas. CTest runs the file comparison in test_headless_smoke_decode.

Leak check¶

LeakSanitizer does not run on macOS with Apple silicon, so the leak check is a Linux job of the CMake workflow, leak check (Linux). It builds the application, test_characterization, test_networkpresenter and test_runtimecanvas in a Debug configuration with -DEGTRAIN_ENABLE_SANITIZERS=ON, starts them with ASAN_OPTIONS=detect_leaks=1, and fails on any leak or double free. It has three parts:

  • tools/e2e/leak_check_smoke.py runs every scene directory below EGTRAIN/QEGTRAIN/Scenes headless, once, with -h 600 --detailed-trajectories. A scene fails when its log holds a LeakSanitizer or AddressSanitizer report, when the process exits with a code other than 0, or when it prints no End of Simulation. All scenes run before the script fails, so one start lists every failing scene.

  • CTest runs characterization_repeatable, characterization_repeat_paimpol, characterization_repeat_milano_paimpol and characterization_repeat_netherlands. Each builds and runs scenes one after the other in one process (see Characterization tests), which is the scene reload. They cover the line fixture, Paimpol, Assignment, Milano-Brescia and Netherlands. Copenhagen and Amsterdam_Hilversum_Student run headless once and are not reloaded.

  • CTest runs test_networkpresenter and test_runtimecanvas on the offscreen platform. They draw the track preview and the items of a run on a canvas, apply the steps of a run and of its replay with a selection on it, and clear the canvas again, twenty times or more in one process. After each clear every registry, every pointer and the scene must be empty, and an item or container that the clear does not release is a leak.

The job runs only in the nightly and the manual run, because the sanitizer build and the instrumented runs take longer than the pull request checks. To check a branch before a merge, start the workflow by hand from the Actions tab, or with gh workflow run cmake.yml --ref BRANCH; the other legs start with it. The artifact leak-check-logs holds one SCENE.log per scene and ctest-reload.log and ctest-canvas.log, also when the job fails.

tools/e2e/lsan_suppressions.txt lists the known leaks. Add one rule for each, with a comment that names the cause and the change that removes the leak, or the library that owns it. A leak of the simulation is fixed, not listed.

On macOS, leaks --atExit -- COMMAND lists the leaks of one run of a normal build. It exits with status 1 when it finds any.

ThreadSanitizer¶

CI runs no ThreadSanitizer. Run the live code under it before a change to the threads of the stream (the server, the step loop in DispatchController or RunControl), in a build directory of its own:

cmake -S . -B build-tsan -DEGTRAIN_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS=-fsanitize=thread -DCMAKE_EXE_LINKER_FLAGS=-fsanitize=thread
cmake --build build-tsan --target QEGTRAIN live_client test_liveserver test_livecommand test_livereplay
ctest --test-dir build-tsan -R '^test_live(server|command|replay)$' --output-on-failure

Qt is not instrumented, so a window run reports data races in ConsoleWidget and in Qt’s queued calls. They do not involve the live code. A run under ThreadSanitizer takes far longer than the limits of test_live_stream_smoke. The smoke test stretches its waits by EGTRAIN_TEST_TIMEOUT_SCALE, so configure with -DEGTRAIN_TEST_TIMEOUT_SCALE=100 before you run it, and put log_path in TSAN_OPTIONS to keep the reports.

Completed-run replay¶

What the Replay row shows and how a user works with it is in Replay a completed run. This section keeps what a developer needs.

The label beside the slider names the selected frame time and keeps the width of its longest text, so the slider does not change its width while the selection moves. The text below the controls does not depend on the selected time, so the row keeps its height while the user seeks. A replay seek explicitly restores historical operational overlays; normal completion does not. Future or exited trains do not appear on layer toggles or drive Follow station emphasis.

The history (app/GuiReplayHistory) records every fifth simulated second and the last one, in a compact form. What is the same for the whole run (identity and static data of trains, the section and direction of each signal, section ids, platforms) is stored once per run in a layout. Each frame stores only flat arrays of the values that change: train positions, speeds and occupied arcs, signal codes, levels and failure flags, section flags, platform queues, passenger states. Strings that vary are stored once in a string table. atOrBefore rebuilds an ordinary snapshot from this form, so the window uses the same snapshot type as in a live run. It keeps the last rebuilt snapshot, and a snapshot that a caller still holds is not rebuilt, so asking again for the same frame returns the same object. A change of the static data between frames (a different number of trains, a renamed train) starts a new layout; older frames keep theirs. Adding a field to a snapshot type stops the build of GuiReplayHistory.cpp and of the round-trip test until the field is stored.

The budget is 128 MiB of accounted payload and there is no frame count limit. When a run does not fit, the oldest frames are dropped and the history reports the interval it still covers (firstTime, lastTime, evictedBeforeTime). Accounting includes the layouts, the string table and the capacities of the frame arrays, not allocator bookkeeping, container nodes, shared-pointer control blocks or the rebuilt snapshots that callers hold, so 128 MiB is not a precise resident-memory limit; for the scenes below the heap in use was 1.1 times the accounted bytes. If one frame, with its layout and strings, exceeds the budget, replay is unavailable with an explanation; the simulation continues. A run without a window (-g 0) builds no snapshots and no replay frames, because nothing reads them. app/ReplayCoverage.h turns the interval the history still covers into the words of the row for a whole run, for a run whose first part was dropped and for a run that cannot be replayed, and into the tooltip of Start; the window reads the history, asks for the texts and writes them into the two labels and the tooltip.

Measured on a full run of each committed scene at the default horizon (-g 1, -pax 0, Apple silicon, release build). “Complete snapshots” is what the same frames would need as ordinary snapshot objects. The rows for Milano_Brescia, Copenhagen and Netherlands come from runs without a signalling area; the committed scenes have one.

Recording a frame took 1 to 30 microseconds (Copenhagen and Netherlands: 21 to 30), once per five steps, on the simulation thread; rebuilding a frame took 1 to 34 microseconds on the interface thread.

Close, New and Open during a run¶

What a user sees when a command waits for a run to stop is in Close, start a new case or open another during a run. test_close_during_run_smoke closes the window during an autostarted run: the close request has to return with the run still stopping, and the application has to exit by itself afterwards.

Editor Smoke Test¶

tools/e2e/editor_smoke.sh

The script starts the application with the editor smoke hook and a settings folder of its own. The first argument is an optional scene directory; the default is Assignment_Gvc_Gdg_Ut, and QEGTRAIN_E2E_SCENE_ALT names the second scene, Copenhagen by default. The application creates, edits, validates, saves and reloads cases through the editors. It then edits a copy of the first scene in each editor and checks that every edit is one step of the history, that Undo and Redo return the scene to the state before and after each step (the bytes that Save writes, the editors, the validation, the unsaved mark and the run results), that a stop dialog that is accepted is one step and one that is cancelled is none, that Save keeps the history, and that a new edit after Undo, a failed open, an open and a new scene change the history as Window flow describes. It then names a folder for recovery copies of its own and checks autosave on a bundle copy of the scene (E2E_EDITOR_RECOVERY_OK): that a run with no folder named keeps no copies; that an edit leads to one copy that names the scene and its source and holds the edits, while the file of the scene stays as it was; that Undo to the saved state, Save, an open of the same scene and a new scene each remove or replace the copy; that Discard followed by an open that fails and Cancel keep it; that closing the window leaves no copy; that Decide Later keeps a copy that an ended window left and Discard removes it; that Recover opens the copy as an unsaved scene without a file, with Save As starting at the original; and that a folder that cannot be made is reported once while the editing goes on. Next it checks the layout of the editors: the main window does not grow beyond 1280 by 800 pixels when an editor dock is shown at the normal and at 1.5 times the font size, a floated dock stays within 750 by 600 and keeps its scroll area, the Add button of the Passengers editor is in view, and the buttons of the Infrastructure editor for Blocks and Routes sit under its table without sideways scrolling. In the docked editor all of them, including the four buttons of the route sections, are in the first view. In the floating dock of 750 by 600 the table buttons and the block buttons are in the first view, and the route section buttons are reached by scrolling to the end of the editor. Last, it opens each editor dock, moves the focus through its fields with Tab, scrolls, floats and resizes the dock, resizes the main window and closes and reopens the dock, and requires that the modified flag and the revision of the scene stay as they were.

The smoke passes when the application exits with status 0, prints E2E_EDITOR_SMOKE_OK and prints the marker of every facet, the last being E2E_EDITOR_UNTOUCHED_OK. The application output goes to ${TMPDIR:-/tmp}/qegtrain-editor-smoke-e2e.log. On a failure the script prints the end of that log, which holds E2E_EDITOR_SMOKE_FAIL: <facet>: <message> when the application reported the failure.

CTest runs the script as test_editor_smoke on macOS and Linux with QT_QPA_PLATFORM=offscreen. Run it alone with ctest --test-dir build -R test_editor_smoke --output-on-failure. The script takes the application from QEGTRAIN_APP. The release workflow also runs it as a step of its own.

Recovery Smoke Test¶

python3 tools/e2e/recovery_smoke.py build/QEGTRAIN.app/Contents/MacOS/QEGTRAIN build/scene_tool

The script ends a window with unsaved edits without closing it and starts the application again. Every run of the application gets a recovery folder and a settings folder of its own (QEGTRAIN_RECOVERY_DIR and QEGTRAIN_E2E_SETTINGS_DIR), so no run meets the copies of a user, and an interval of 100 ms (QEGTRAIN_RECOVERY_INTERVAL_MS). QEGTRAIN_E2E_RECOVERY names the script that the application runs in the window, and QEGTRAIN_E2E_RECOVERY_ANSWER and QEGTRAIN_E2E_RECOVERY_SAVE_AS say how the next run answers the recovery prompt and where it saves the recovered case. A run that ends in a crash makes three edits to a bundle copy of Assignment_Gvc_Gdg_Ut, waits until the autosave has written its copy and ends with _Exit(137), so no destructor runs and no close event reaches the window. The script checks:

  • Bundle: the next start offers the copy with the path of the bundle and no note, with Recover as the default button. Recover opens an unsaved scene without a file that holds the three edits, Save As starts in the folder of the bundle with its file name, and the bundle keeps its bytes and its modification time. The window closes after Save As, no recovery folder is left and the next start has no prompt.

  • New case: a case that was never saved is offered as New case study, not saved and recovered in the same way.

  • Changed original: an original that changed, is newer than the copy or is missing is named in the prompt, and Decide Later is the default button for the first two. Decide Later keeps the copy, Recover opens it, Discard removes it, and the original is not touched.

  • Discard at close: Discard in the question about unsaved changes leaves no copy, and the next start has no prompt.

  • Unwritable folder: when the folder for the copies cannot be made, the window reports it once, the edits go on and a run completes.

CTest runs the script as test_recovery_smoke on macOS and Linux, with the application and scene_tool from the build, and it takes about 25 seconds. A failure prints the end of the output of the run that failed. The scripts of the application are in EGTRAIN/QEGTRAIN/tests/e2e/Recovery.cpp and the answer to the prompt in Dialogs.cpp. The editor smoke covers the same paths in one process.

The recovery folder is below the local application data folder of the user. An operating system backup or a sync tool that includes that folder can copy recovery files, which hold the case data of the scenes in them.

CI and release branches¶

  • main is the validation branch. Pull requests build the project and run the CTest suite without the tests labelled network (those run on Windows only), in parallel, on macOS, Windows (MSVC, Qt 5.15.2, vcpkg x64) and Linux (Ubuntu with apt Qt 5), unless every changed file matches the documentation rule below. The suite holds the end-to-end smokes of the committed scenes (see Simulation Smoke Test and Scene Roundtrip Smoke Test). The docs job runs tools/docs/check_docs.py on every pull request, documentation-only ones included. The same checks run on main once a night (02:17 UTC) and when started by hand from the Actions tab (workflow_dispatch); both always build, and both also start the leak check on Linux. A push to main starts no run. A scheduled workflow runs on the default branch only, and GitHub pauses schedules in a repository without activity for 60 days. The three legs run independently (fail-fast: false) and follow the same rule. A newer push to a pull request cancels its running checks; a scheduled or manual run is never cancelled. After the tests, the Windows leg also makes the request of the HTTPS update check in a step of its own. A failed leg uploads ctest.log and the GUI autostart log as an artifact named after the leg. Do not make any of these legs a required check; main requires the result checks described below.

  • The format check (format.yml) runs tools/format.py for a pull request to main that changes EGTRAIN/QEGTRAIN/, .clang-format, .clang-format-ignore, tools/format.py or format.yml, and when started by hand.

  • The tidy check (tidy.yml) runs tools/tidy.py for a pull request to main that changes EGTRAIN/QEGTRAIN/, the root CMakeLists.txt, .clang-tidy, tools/tidy.py or tidy.yml. A pull request analyses the changed sources and the sources that include a changed header; the nightly run (02:37 UTC) and a manual start analyse every source. The run installs clang-tidy 23.1 from apt.llvm.org and lists the findings; the local command and the checks are described in the coding guidelines. The result check is named Tidy result.

  • The documentation workflow (docs.yml) builds the documentation site for every pull request, fails a pull request that adds undocumented classes or members to the files it changes, and publishes the site to gh-pages: dev/ from main, and <version>/ and latest/ after a successful release.

  • A pull request to main that changes a packaging input also runs the package check (package-check.yml). The inputs are the workflow files package-check.yml, package.yml and release.yml, tools/release/, installer/, Info.plist.in, EGTRAIN/QEGTRAIN/update/ and EGTRAIN/QEGTRAIN/app/main.cpp. The check also runs once a night on main and can be started by hand, which covers changes that reach the packages through other files, such as the root CMakeLists.txt. The check selects the version as a release run that does not publish does (the CMake baseline, through tools/release/version.py) and calls the reusable workflow package.yml twice: with qt: '5', as the release workflow does, and with qt: '6' in the job Qt 6 packages (not required), whose artifact names end in -qt6 and which Package check result does not wait for. A green check proves that the macOS, Windows and Linux packages build, pass the completeness checks of their jobs and are uploaded as artifacts of the run. The Windows package job also fails when the software OpenGL, ANGLE or Direct3D compiler libraries, Qt Quick, QML or virtual keyboard files or vc_redist.x64.exe are in the package or when a program file imports a DLL that is neither in the package nor part of Windows, starts a copy of the package with tools/release/package_start_smoke.py, makes the request of the HTTPS update check from that copy, and prints the number of files and bytes of the package in its job summary. It also prints the signature state of QEGTRAIN.exe, egtrain_update_helper.exe and scene_tool.exe with tools/release/verify_signatures.ps1 -Report, which fails for no file. A push to production or a v* tag runs the job sign-windows when the repository variable WINDOWS_SIGNING is signpath; it signs those three files and replaces the uploaded directory with one that holds them (see Code signing). Every other run skips it. The Windows finalize job (finalize-windows) then downloads that directory, compiles installer/egtrain.iss with Inno Setup (the copy on the runner image, or a pinned version from Chocolatey when the image has none; the script needs 6.3 or newer) into EGTRAIN-Setup-<version>-x64.exe, runs tools/release/installer_smoke.ps1 on it (see Installer smoke), writes EGTRAIN-Portable-<version>-x64.zip from the same directory with build_release_assets.py --payload, extracts that archive and starts the extracted program with the same start script, and uploads the installer and the archive as the artifacts EGTRAIN-windows-x64-installer and EGTRAIN-windows-x64-portable. The smoke needs an installer of a higher version for its upgrade check, so the job compiles a second one with the next patch version and uploads only the first. When the job fails, it uploads the logs of Setup and of the uninstaller as the artifact finalize-windows-diagnostics. When sign-windows succeeded, the job sign-windows-installer then sends the uploaded installer to the signing service, requires valid signatures on the signed installer and on the three program files of the payload, and only then replaces the installer artifact with the signed file. The installer smoke runs on the installer before it is signed. The macOS package job builds for macOS 26 (-DCMAKE_OSX_DEPLOYMENT_TARGET=26.0) and writes the minimum system version of the executable into the LSMinimumSystemVersion key of the property list, so the app needs macOS 26 or later. It copies scene_tool into the app, to Contents/MacOS/scene_tool, puts LICENSE and THIRD_PARTY_NOTICES.md in Contents/Resources, and removes the virtual keyboard input plugin with the Quick and QML frameworks, and the WebP and TIFF plugins with their libraries, from the app. All of this comes before the one signature, which tools/release/sign_macos.sh makes (see macOS signing script). After the signature the job fails when one of the removed files is in the app, runs scene_tool on the Paimpol scene of the app without the GUI, starts a copy of the app with the same script, and prints the number of files and bytes of the app before and after the removal in its job summary. In a push to production or a v* tag it then notarizes and staples the app when the environment holds notarization credentials (see macOS notarization script). It builds EGTRAIN-<version>-macOS-arm64.dmg from the app with tools/release/make_dmg.py --layout, and no later step changes the app. With a Developer ID identity the image is signed, and with notarization credentials it is notarized and stapled. The job mounts the image read-only and detaches it on every path. It checks that the volume holds only QEGTRAIN.app, the link Applications and the hidden file .DS_Store, that this file equals tools/release/dmg/DS_Store, that the app in the image and a ditto copy of it pass codesign --verify --deep --strict, that the property list of the app in the image declares .egscene as its one document type (CFBundleDocumentTypes) and exports the type com.egtrain.simulator.egscene, which conforms to public.data only (UTExportedTypeDeclarations), that the copy has the version and the identifier of the build, its programs and the guide, and that the copy runs Paimpol without the GUI to End of Simulation. The image is the only file of the artifact QEGTRAIN-macos-arm64; no zip is made. The Linux package job extracts its AppImage and starts the extracted image with the same script on a virtual display, after the script has checked that every Qt 5 and ZeroMQ library of the programs and plugins comes from the image. The start in each of the three package jobs is the headless run and the window start, with no CSV or PNG export, because a release build has no test hooks to ask for one. The check does not show how the SVG icons look, typing into text fields, the native file dialogs, how Finder presents the disk image, whether a double-click on a .egscene file in Finder opens EGTRAIN, or a start on a machine without Qt or a display server; the clean-install rehearsal in the release testing checklist covers them. After the three packages are built, the job release-assets downloads the artifacts and runs tools/release/build_release_assets.py on them with the command line of the release job (--artifacts artifacts --output release-assets). The Windows package arrives as a directory with QEGTRAIN.exe at its top level. A green check therefore also proves that the script accepts the real packages, the installer and the portable archive, that the archive holds the files of the payload with the same bytes, that the script builds a manifest that the application accepts by its rules for the file list and the package sizes, and that the assets it writes are exactly the files that a release publishes. It does not prove a release: nothing is signed with real credentials (the macOS bundle is signed ad hoc, as in a release without a certificate), nothing is published, and the check has read permission only. It does not prove the release job either: that job runs only on a push to production or a v* tag, so its steps (the script step, the glob that publishes release-assets/*, the creation of the release) are first run by a release. The finalize job extracts the archive with Python, not with the PowerShell command that the application uses; only the unit test of the script extracts an archive with that command, on the Windows leg of the CMake workflow. The runner account is an administrator, so the check does not show that a standard user installs without an elevation request. It runs on a machine with the Visual C++ runtime, so it does not show that the package starts on a machine without it. It does not show how Windows presents the installer (for an unsigned download, the SmartScreen screen), the Start Menu entry or the entry in the list of installed apps. The smoke reads the registry keys of the .egscene file type but opens no file, so it does not show that a double-click on a .egscene file in Explorer opens EGTRAIN. The installer and portable rows of the release testing checklist cover the rest on a Windows machine. A release still runs only from release.yml. A newer push to the pull request cancels the running check.

  • production is the release branch. Its full pipeline packages macOS, Windows, and Linux applications, runs CTest, which holds the smoke suite, and the sanitizers, validates the scene bundles, and publishes a stable vX.Y.Z release. The three package jobs and the Rehearse Linux job, which runs the clean-install steps on the Linux package, are in .github/workflows/package.yml, which release.yml calls from its package job with the selected version. The Windows package job uploads the assembled directory as the artifact QEGTRAIN-windows-x64-payload, and the Windows finalize job builds the installer and the portable archive from it and uploads them as EGTRAIN-windows-x64-installer and EGTRAIN-windows-x64-portable. The release job builds the files of the release from the downloaded artifacts with tools/release/build_release_assets.py and publishes the files it writes; the portable archive is written only by the script. Before building, the pipeline increments the highest patch version among the CMake baseline, existing stable tags, and reserved release versions. Every build job, the package metadata and the update manifest use that same version. Local builds use the baseline unless configured with -DEGTRAIN_VERSION=X.Y.Z. update-manifest.json has one entry per distribution key under assets, each with name, sha256 and size. The running copy picks its entry by key and downloads the asset that name gives. The keys are windows-x64 (portable package), windows-x64-installer, macos-arm64 and linux-x86_64. A Windows copy with installed-by-setup.ini next to QEGTRAIN.exe is installer-managed (currentDistribution in update/Distribution.cpp) and takes windows-x64-installer; every other copy takes the key of its platform, which for a portable Windows copy is windows-x64. An installer-managed copy does not update itself by replacing files: it downloads the installer and the update helper runs it. The installer is the only intended source of that file, and the package payload and the portable archive must not contain it. The updater accepts a name only when it fits a pattern of its key, where <version> is the version of the manifest, which must equal the release tag without its leading v. The same patterns decide which release assets the update check keeps (kAssetPatterns in update/ReleaseInfo.cpp). The table lists the names a release may use; a name outside it needs a new application:

    Key

    Accepted names

    windows-x64

    QEGTRAIN-windows-x64.zip, EGTRAIN-Portable-<version>-x64.zip

    windows-x64-installer

    EGTRAIN-Setup-<version>-x64.exe

    macos-arm64

    QEGTRAIN-macos-arm64.zip, EGTRAIN-<version>-macOS-arm64.dmg

    linux-x86_64

    QEGTRAIN-linux-x86_64.AppImage

    A name with a path separator, another version or another kind of file is rejected. The manifest has no field for the kind of package; the key and the pattern decide it. The manifest of a published release keeps working because its names are in the table. Staging handles the archives, the macOS disk image and the AppImage. The installer is checked against the manifest and staged as it is, without extraction. A package whose name ends in .dmg is mounted read-only below the staging folder with hdiutil attach -readonly -nobrowse -noautoopen, QEGTRAIN.app is copied from the root of the volume with ditto, and the volume is detached on every path (by force on the last attempt). The zip package of earlier releases, which holds QEGTRAIN-Lebanon/QEGTRAIN.app, can still be staged. update-manifest.json also lists the files of the Windows package. Before the updater replaces an installation, it requires every listed file and a fixed set of runtime files (requiredRuntimeFiles() in update/WindowsStaging.h) in the extracted package. Keep that set in step with the package verification in the Windows package job.

  • Production and tag releases run serially. A stale production run cannot publish after the branch advances, and an existing production release tag cannot be overwritten. If a failed-job retry encounters a used version, rerun all jobs on the latest production commit to allocate a new version.

  • v* tags supply their application version explicitly. Tags containing a prerelease suffix remain prereleases and are not offered by the updater. workflow_dispatch validates the pipeline without publishing.

  • Releases remain drafts until every package and scene bundle is uploaded. Stable production releases then appear in the application’s update checks.

Pushes and pull requests to production skip the release workflow when changes are limited to Markdown files (**.md), docs/, the root LICENSE, or .github/ISSUE_TEMPLATE/. Mixed changes still run the full workflow, as do changes to source, tests, scenes, build settings, or workflows. Documentation-only production pushes do not publish a new release. Updated packaged guides ship with the next release; v* tags and manual release runs are not filtered by changed paths.

Required checks on main¶

Every pull request to main starts the CMake, Format and Package check workflows; their triggers have no path filter. The first job of each, changes, compares the files of the pull request with the rule of the workflow, and the real jobs skip when the rule selects nothing:

  • CMake builds unless every changed file is a Markdown file (**.md), under docs/ or .github/ISSUE_TEMPLATE/, or the root LICENSE. Its docs job checks the documentation on every pull request.

  • Format runs for the files of the format check, listed above.

  • Tidy runs for the files of the tidy check, listed above.

  • The package check runs its jobs for the packaging inputs, listed above.

A nightly or manual run always does its jobs. The condition of a job is evaluated before its matrix is expanded, so a skipped build job would be listed as build (${{ matrix.name }}). The three legs of the CMake workflow therefore always start, and their steps skip.

The last job of each workflow reports one check: CMake result, Format result, Tidy result or Package check result. It runs whatever the other jobs did, fails when any of them failed or was cancelled, and succeeds when they succeeded or were skipped. A documentation-only pull request gets four successful result checks without a build when the documentation check finds nothing. main requires these four checks and no others, so a pull request can merge automatically when they are green. Do not require the build legs, the format job, the tidy job or the package jobs: a required check that no run reports under its own name leaves the pull request waiting forever.

Release assets script¶

tools/release/build_release_assets.py builds the files that a release publishes from the artifacts of the package jobs, and writes the portable Windows archive for the Windows finalize job:

python3 tools/release/build_release_assets.py --version X.Y.Z --artifacts DIR --output DIR
python3 tools/release/build_release_assets.py --version X.Y.Z --payload DIR --output DIR

--artifacts holds one directory per artifact, as actions/download-artifact makes them when it is given no artifact name:

  • QEGTRAIN-windows-x64-payload/: the assembled Windows package, with QEGTRAIN.exe at its top level, uploaded by the Windows package job

  • EGTRAIN-windows-x64-portable/EGTRAIN-Portable-X.Y.Z-x64.zip

  • EGTRAIN-windows-x64-installer/EGTRAIN-Setup-X.Y.Z-x64.exe

  • QEGTRAIN-macos-arm64/EGTRAIN-X.Y.Z-macOS-arm64.dmg

  • QEGTRAIN-linux-x86_64/QEGTRAIN-linux-x86_64.AppImage

  • EGTRAIN-scenes/: the .egscene files of the case studies

Other directories are ignored. --output must not exist or must be an empty directory, and the script writes nowhere else. Afterwards it holds exactly the files of a release: the packages named above, the .egscene files of the case studies and update-manifest.json. The packages and the scene bundles are copies. The sha256 and size of each package in the manifest come from the file in --output. The files of the windows-x64 entry are the members of the portable archive, sorted by their full path as a string (a.b comes before a/b). The windows-x64-installer entry has no files. The script prints the name and size of each file. The release job and the package check run it with --artifacts artifacts --output release-assets on the artifacts they download, and the release job publishes the files of the output directory.

--payload takes the assembled Windows package and writes EGTRAIN-Portable-X.Y.Z-x64.zip into --output: one member per file with forward slashes, in the order of the sorted file list, no directory entries and no top-level folder. The Windows finalize job runs it on the directory that it also gives to Inno Setup, so the installer and the archive hold the same files. The --artifacts form copies the archive and checks that it has exactly the members of the payload artifact, in that order, with the same bytes.

Every input is checked before --output is created:

  • the version has the form X.Y.Z that tools/release/version.py accepts;

  • each file above exists and is not empty, the artifact directories hold no other file, and the payload holds regular files and directories only (a link is an error, and so is a directory that cannot be read);

  • the portable archive is a readable archive that holds the files of the payload and nothing else, with the same bytes;

  • the file list of the Windows package has the rules of parseManifestFiles in update/ReleaseInfo.cpp: at most 4096 entries, each path at most 260 UTF-16 code units, no : and no NUL, no empty, . or .. segment, and QEGTRAIN.exe in the list. A backslash is also rejected, where the application would read it as a slash, because the list names the members of an archive that uses forward slashes only;

  • each package is between 1 byte and 2 GiB, the limit of parseUpdateManifest in update/ReleaseInfo.cpp. With --payload the size of the archive is checked once it is written.

The script does not check the fixed runtime file set (requiredRuntimeFiles() in update/WindowsStaging.h): the Windows package job verifies it before it uploads the package.

The test is tools/release/test_release_assets.py. It builds a small artifact tree, with the portable archive written by the script, runs the script on it and checks the rules directly. Run it with ctest --test-dir build -R test_release_assets --output-on-failure.

Disk image script¶

tools/release/make_dmg.py builds the macOS disk image from a finished QEGTRAIN.app:

python3 tools/release/make_dmg.py --version X.Y.Z --app PATH/QEGTRAIN.app --output DIR [--layout]

The image is DIR/EGTRAIN-<version>-macOS-arm64.dmg, one of the names in the table of accepted names above. It is a compressed, read-only (UDZO) HFS+ image with the volume name EGTRAIN. The volume holds QEGTRAIN.app and Applications, a symbolic link to /Applications to drag the app onto, and nothing else: no scene folder, no .egscene file, no scene_tool and no guide. The script copies the bundle with ditto, as the package job does, and does not change it afterwards, so a signed app keeps a valid signature. The script prints the name and size of the image.

With --layout the volume also holds the hidden file .DS_Store, a copy of tools/release/dmg/DS_Store. It tells Finder to show the volume as an icon view of 600 by 360 points with icons of 128 points and without toolbar, sidebar, path bar and status bar, with QEGTRAIN.app on the left and Applications on the right at the same height. There is no background picture and no volume icon. Without --layout Finder places the two icons itself. The file is written without Finder by tools/release/dmg/make_ds_store.py, which needs the ds_store package. The package is not a dependency of the repository or of CI, so run the script in a throwaway environment and commit the result:

uv run --no-project --with ds_store python tools/release/dmg/make_ds_store.py tools/release/dmg/DS_Store

The sizes and positions are constants at the top of that script. How the window looks is checked by opening the image on a Mac.

These checks run before the script creates anything:

  • the version has the form X.Y.Z that tools/release/version.py accepts;

  • --app is a directory named QEGTRAIN.app that holds Contents/Info.plist and the directory Contents/MacOS;

  • --output is not a file, and the image does not exist in it yet. The script never overwrites a file;

  • with --layout, tools/release/dmg/DS_Store is a file;

  • ditto and hdiutil are on the path. Both are macOS tools, so the script runs only on macOS.

Then it creates --output if needed, stages the app, the link and, with --layout, .DS_Store in a temporary folder that it removes on every exit, and runs hdiutil create on the folder. Each tool gets 120 seconds, and only its exit status decides whether it worked: hdiutil prints deprecation notices on standard error and still exits with 0. When hdiutil fails or times out, the script removes the partly written image and exits with the command and its error text.

Two images made from the same bundle have the same file name, volume name and contents. The script does not promise equal image bytes. It sets no background picture, volume icon or licence text, and it does not sign, notarize or upload anything. The macOS package job in package.yml calls it once the app is signed and checked, with --output build/dmg --layout, and uploads the image as the artifact QEGTRAIN-macos-arm64.

The test is tools/release/test_make_dmg.py. On macOS it signs a small fixture bundle (a program that exits with 0, a data file and a symbolic link inside the bundle), builds the image and mounts it read-only below a temporary folder. It checks the file name, the format, the volume name, the entries at the top of the volume, that no .egscene file or Scenes folder outside the app is on the volume, and that the app in the image equals the fixture in its paths, file bytes, link targets and permission bits. It also checks that codesign --verify --deep --strict passes on the app in the image and on a ditto copy taken from it, and that the copy runs. It builds a second image with --layout and checks that its .DS_Store equals the committed file and that the app in it is unchanged. On every platform it checks the file name against kAssetPatterns in update/ReleaseInfo.cpp, the input rules, the message for a missing tool, and the command lines, the link, the staged .DS_Store and the handling of a failing or timed-out command, with stand-ins for ditto and hdiutil, and that the committed layout file names the app and the link. Run it with ctest --test-dir build -R test_make_dmg --output-on-failure.

macOS signing script¶

tools/release/sign_macos.sh <app> signs the app in the macOS package job (step Sign the app). Without MACOS_SIGNING_IDENTITY, or with it empty, it runs codesign --force --deep --sign -, an ad-hoc signature that carries no publisher. With the variable set to a Developer ID Application identity from a keychain on the search list, it signs each Mach-O file and each nested .framework, .app and .xpc bundle on its own, with --options runtime --timestamp: first those in Contents/Frameworks, the deepest first, then those in Contents/PlugIns, then the programs in Contents/MacOS (egtrain_update_helper and scene_tool), then the main executable, and finally the bundle, without --deep. It stops before it signs anything when a Mach-O file is somewhere else in the bundle, and it prints no credential.

In the workflow, a push to production or a v* tag runs the job in the environment macos-signing. The step Import the signing certificate reads the environment secrets MACOS_CERTIFICATE (a base64 encoded .p12 file with the private key) and MACOS_CERTIFICATE_PASSWORD, and the variable MACOS_SIGNING_IDENTITY (the name of the identity, as security find-identity prints it). It imports them into a keychain of its own, passes the identity to the later steps, and the last step of the job deletes the keychain. Without a certificate the step does nothing and the app keeps the ad-hoc signature. The step Verify the signature prints the identifier, authority and team of the app, and requires an ad-hoc signature without an identity and a Developer ID Application authority, a team, the hardened runtime and a timestamp with one. Neither the workflows nor the release scripts remove the quarantine attribute or turn Gatekeeper off; test_ci_workflow checks it.

The test is tools/release/test_sign_macos.sh. It builds a fixture bundle with a framework, a flat library, a plug-in, two programs next to the main one and a data file, and runs the script with a codesign in front of the real one that records its arguments and turns --timestamp into --timestamp=none, because a secure timestamp needs Apple’s server. It checks that the ad-hoc path makes one --deep call and that the bundle verifies with codesign --verify --deep --strict. It runs the identity path with the identity -, so that the real tool signs without a certificate, and compares the calls with the expected order and options, checks that the bundle verifies and that every piece of code has the hardened runtime. A recording that signs nothing shows that an identity name with spaces and parentheses reaches each call as one argument and that no credential in the environment is printed. It also checks that Mach-O code in Contents/Resources stops the script and that a missing app is refused. The test makes no certificate or keychain, so it does not show that a Developer ID certificate signs, that the timestamp server answers or that Apple accepts the app. Run it with ctest --test-dir build -R test_sign_macos --output-on-failure.

macOS notarization script¶

tools/release/notarize_macos.sh <app or disk image> notarizes a file that is signed with a Developer ID Application identity. It stops when the signature is not one, sends the file to Apple with xcrun notarytool submit --wait (an app as a zip archive made with ditto, an image as it is) and requires the verdict Accepted. For any other verdict it prints Apple’s log of the submission and fails. Then it staples the ticket with xcrun stapler staple, tried up to five times because Apple may not hand out the ticket at once, and checks it with xcrun stapler validate and spctl --assess (--type execute for an app, --type open --context context:primary-signature for an image). Any failing command fails the script.

The credentials come from the environment and nowhere else. The script uses either an App Store Connect API key, with MACOS_NOTARY_KEY (the text of the .p8 file), MACOS_NOTARY_KEY_ID and MACOS_NOTARY_ISSUER_ID, or an Apple ID, with MACOS_NOTARY_APPLE_ID, MACOS_NOTARY_TEAM_ID and MACOS_NOTARY_PASSWORD (an app-specific password). The API key wins when both are complete. With none of the six set, or all of them empty, the script says that it skipped the file and succeeds, so the file is not notarized. With some set and neither group complete it fails and names the missing variables. It prints no value, and it writes the key to a file in a private temporary folder that it removes on every exit.

In the workflow, the credentials belong to the environment macos-signing: the key and the password are environment secrets, the other four are environment variables. Two steps read them and nothing else does. Notarize the app runs after Start the package and before Build the disk image, so the app in the image already carries its ticket and keeps it when it is copied out of the image offline. After the image is built, Sign the disk image signs it with the identity of the import step (codesign --force --timestamp --sign), or leaves it unsigned when there is no identity, and Notarize the disk image sends it as a second submission. Both notarization steps run only for a push to production or a v* tag, have a time limit of 60 minutes, and have no condition on a credential and no continue-on-error: a release job without credentials succeeds and ships files that are not notarized, and one with credentials fails when any command of the script fails, so a file that Apple rejected is never published as notarized. Verify the disk image then checks the signature of the app in the finished image as before.

The test is tools/release/test_notarize_macos.sh. It puts stand-ins for codesign, xcrun and spctl in front of the real tools, so nothing reaches Apple, and uses the real ditto. It checks the arguments and the order of the calls for an app with an API key and for an image with an Apple ID, that the app goes to notarytool as an archive that holds it and the image as it is, that the key file has the mode 600 and is gone afterwards, that the script skips without credentials and fails for partial ones, wrong calls, a file without a Developer ID signature, a verdict of Invalid, no verdict, a failing notarytool, a ticket that stapler hands out only at the third attempt or never, a ticket that does not validate and a refusal by Gatekeeper, and that no value of a credential reaches the output. It runs on macOS only. The package job runs it in the step Test the notarization script, and it is not registered in CTest. It does not show that Apple accepts the app, that the ticket attaches to the files or that Gatekeeper accepts them: the first run with real credentials is the first proof of that. Run the test with bash tools/release/test_notarize_macos.sh.

Installer script¶

installer/egtrain.iss is the Inno Setup script of the Windows installer. Compile it on Windows with Inno Setup 6.3 or newer:

ISCC.exe /DVersion=X.Y.Z /DPayload=<package directory> [/O<output directory>] installer\egtrain.iss

/DVersion is the release version. /DPayload is the absolute path of the assembled Windows package, the directory that the Windows package job uploads as QEGTRAIN-windows-x64-payload. Setup writes EGTRAIN-Setup-<version>-x64.exe, the name in the table of accepted names above, to installer/Output or to the /O directory. Windows installer script describes the parameters, what the installer does and the Setup switches for a silent install.

The installer is for the current user and needs no administrator rights. It installs the package directory as it is into %LOCALAPPDATA%\Programs\EGTRAIN by default, adds a Start Menu entry and an optional desktop shortcut, and registers an uninstall entry under the current user. It also associates the .egscene file type with {app}\QEGTRAIN.exe for the current user, which the uninstaller removes. It replaces the Scenes folder of the installation folder on every install and runs no program. Setup shows the GPL-3.0 text of LICENSE on a licence page, and the Windows package job copies LICENSE into the package, so the installed folder and the portable archive hold it. The Windows finalize job of package.yml compiles the script, and tools/release/installer_smoke.ps1 installs the result on the runner.

The test is tools/release/test_installer_script.py. It reads the script, installer/installed-by-setup.ini, docs/development/windows-installer.md, kAssetPatterns in update/ReleaseInfo.cpp, LICENSE and the Windows package job of .github/workflows/package.yml as text, looks for the icon file, and checks that the script names LICENSE as its licence file and the package job copies and checks it, and that:

  • the script is ASCII and names neither HKEY_LOCAL_MACHINE nor a parent folder;

  • it has only the sections Setup, Tasks, Files, InstallDelete, Icons and Registry, so no code, run or uninstall-delete section, and uses only the constants {app}, {userpf}, {userprograms} and {userdesktop}, so nothing is installed for all users, and only the two shortcuts lie outside the installation folder;

  • the preprocessor lines are the #ifndef and #error guards for the two parameters, and the only macros are {#Version} and {#Payload};

  • the [Setup] directives that decide the scope have their pinned values: the AppId, the per-user privilege level with no override, the per-user folder, the 64-bit architecture, closing a running program and the refresh of the file associations (ChangesAssociations). The directives PrivilegesRequiredOverridesAllowed, UninstallFilesDir, CreateUninstallRegKey and Uninstallable are refused, and the icon file exists;

  • the output name is one that kAssetPatterns accepts for windows-x64-installer;

  • the package is installed as it is, with no external or downloaded file, and the marker file is installed next to the program and is not empty;

  • only {app}\Scenes is deleted before an install;

  • the desktop shortcut belongs to a task that is unchecked by default, and the only shortcuts are the two that run {app}\QEGTRAIN.exe;

  • the [Registry] entries are the four of the .egscene file type, all for the current user under Software\Classes, and no others, so no other extension such as .zip is claimed: the default value of .egscene is EGTRAIN.Scene and is deleted on uninstall, with the key only when nothing else is left in it, so that a value of another program stays; the key EGTRAIN.Scene, its DefaultIcon and its shell\open\command are deleted on uninstall; the icon is the first icon of {app}\QEGTRAIN.exe; the open command is "{app}\QEGTRAIN.exe" "%1";

  • the README names /DVersion, /DPayload and installed-by-setup.ini.

The test also runs the rules on the script with CRLF line ends, as a checkout on Windows may have them, and changes the script one line at a time to check that each rule reports the change. It does not compile the script or run an installer, so a green run shows nothing about Inno Setup accepting the file or about an install on Windows. Run it with ctest --test-dir build -R test_installer_script --output-on-failure.

Installer smoke¶

tools/release/installer_smoke.ps1 installs, upgrades and uninstalls the compiled installer on Windows. The Windows finalize job runs it on the installer and on a second installer of the next patch version, both built from the same directory:

tools/release/installer_smoke.ps1 -Installer EXE -UpgradeInstaller EXE -Payload DIR -Version X.Y.Z -UpgradeVersion X.Y.Z [-Work DIR] [-Python NAME]

Run it only on a machine without EGTRAIN. It stops when an uninstall entry, a Start Menu or desktop shortcut, %LOCALAPPDATA%\Programs\EGTRAIN or a key of the .egscene file type (HKCU\Software\Classes\.egscene or HKCU\Software\Classes\EGTRAIN.Scene) exists already. It changes the registry, the Start Menu and the desktop of the current user and removes what it installs. -Work must not exist or must be empty; the script puts a copy of the package, its installation folders, a file outside them and the logs of Setup and the uninstaller below it. It checks:

  • both installers request asInvoker in their manifest;

  • a copy of the package directory, started with package_start_smoke.py as a portable copy is, leaves no key of the .egscene file type in the registry;

  • a silent install (/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /LOG) into a folder with /DIR and without the desktop task leaves one uninstall entry under HKEY_CURRENT_USER that names the folder and the version, none under HKEY_LOCAL_MACHINE, a Start Menu shortcut that starts QEGTRAIN.exe in the folder, no desktop shortcut, and in the folder the files of the package with the same bytes, installed-by-setup.ini and one uninstaller, and nothing else. The default value of HKCU\Software\Classes\.egscene is EGTRAIN.Scene, and the key EGTRAIN.Scene has a display name, the first icon of the installed QEGTRAIN.exe and the open command "<folder>\QEGTRAIN.exe" "%1"; it is not under HKEY_LOCAL_MACHINE. package_start_smoke.py then starts the installed copy. The silent uninstall removes the entry, the shortcut, the file type and the files, and a file beside the folder survives. A file that the program wrote into the folder during the start check may stay with the folder;

  • an install with /TASKS=desktopicon also creates the desktop shortcut, and the uninstall removes it. The script first plants a value of another program in HKCU\Software\Classes\.egscene. It must survive the install and the uninstall, which removes only the default value of that key. After the other uninstalls the key is gone;

  • an install into the default folder, the second installer over it and an uninstall: the upgrade leaves one entry and one folder, the entry shows the higher version, a scene folder that the package does not hold is gone and the files are those of the package. The uninstall leaves a file outside the folder.

The script does not use /CURRENTUSER, because the installer script offers no choice of scope and the switch would change nothing. The account of a CI runner is an administrator, so a run there does not show that a standard user installs without an elevation request. The script compares bytes with fc.exe and computes no hash.

Signature check¶

tools/release/verify_signatures.ps1 checks the Authenticode signatures of the Windows program files in a directory:

tools/release/verify_signatures.ps1 -Directory DIR (-Require | -Report) [-ExpectedSubject SUBJECT] [-Name FILE,...] [-AllowUntrustedRoot] [-NoTimestampCheck]

A file passes when its status is Valid, the digest algorithm of its signature is SHA-256, the signature has a timestamp and the subject of the signing certificate equals -ExpectedSubject. -Name defaults to QEGTRAIN.exe, egtrain_update_helper.exe and scene_tool.exe. -Require needs -ExpectedSubject and exits with 1 when a file fails; -Report prints the findings and exits with 0. The Windows package job runs it with -Report on the unsigned package of every run, and the two signing jobs run it with -Require: sign-windows on the payload, and sign-windows-installer on the signed installer (named with -Name) and on the payload. The other two switches are for tests that sign with a throwaway certificate and must not be used on a release.

test_verify_signatures (tools/release/test_verify_signatures.ps1) runs on Windows only. It creates a self-signed code-signing certificate in the store of the current user, signs copies of the built scene_tool.exe and runs the script on them in a new PowerShell. A copy signed with SHA-256 must pass. An unsigned copy, a copy signed with SHA-1, a check for another subject, a missing file, a check without -AllowUntrustedRoot and a check without -NoTimestampCheck (the copies have no timestamp) must fail, and the output must name the reason. The certificate is never exported or added to a trusted root, and the test removes it with its key. Run it by hand with ctest --test-dir build -C Release -R test_verify_signatures --output-on-failure.

Dependency caches¶

The Windows leg caches the Qt install (through jurplel/install-qt-action, with the same cache entries as the Windows package job) and the vcpkg binary archives in runner.temp/vcpkg-binary-cache. vcpkg names an archive by a hash that covers its own checkout, its CMake and the compiler, and the runner image fixes all three. The key of the vcpkg cache is therefore vcpkg-x64-windows-zeromq-cppzmq-nlohmann-json-<image>-v1, where <image> is ImageOS and ImageVersion of the runner. A new image writes a new entry, and the save step runs when the restore found no entry with the exact key. To start over, for example after changing the vcpkg package list, raise the -v1 suffix by hand in the restore and save steps. An existing key is never overwritten. Homebrew and apt packages are not cached.

All three legs also keep a compiler cache, set up by hendrikmuhs/ccache-action before the configure step: ccache on macOS and Linux, sccache on Windows. The cache value of the matrix names the tool, and each configure step passes it as CMAKE_C_COMPILER_LAUNCHER and CMAKE_CXX_COMPILER_LAUNCHER. The Visual Studio generator ignores a compiler launcher, so the Windows leg configures with Ninja in the MSVC environment of ilammy/msvc-dev-cmd and names cl. Its executable is build/QEGTRAIN.exe, not build/Release/QEGTRAIN.exe. The Release configuration adds no /Zi, so sccache can store its objects. The key of the cache is the leg and the runner image, and the action adds a timestamp, so every run saves a new entry. A run restores the newest entry of its leg and image, or else the newest of its leg. The post step of the action (Post Set up compiler cache) prints the hits and misses of the job. Each entry holds at most 500 MB, and GitHub keeps 10 GB for the repository and removes the entries used least recently first.

The three legs configure with -DEGTRAIN_IPO=OFF. A Release build links with interprocedural optimization by default (link-time optimization, or LTCG with MSVC) when the toolchain supports it; with the option OFF the build skips it. The optimized link generates the code of the whole program again for every test executable, which a compiler cache cannot store, so the pull request checks build without it. The package and release workflows do not pass the option, so the shipped binaries and the package checks are built with it, and so is any other build that leaves the option at its default of ON.

A pull request can restore the caches of its own earlier runs and the caches written on main, not the caches of other branches. A push to main starts no run, so only the nightly or manual run on main writes the caches that the first run of a pull request uses. That is enough: the newest compiler cache of main is about a day old, so a pull request compiles again only what the changes since then affect, and its later runs restore its own cache. The first run after a key change is cold. GitHub removes a cache that no run has used for seven days; the nightly run keeps the entries in use.

Verification Gates¶

To run what CI runs, use ctest --test-dir build --output-on-failure (add -C Release with a multi-config generator, and -j N to run tests side by side). For a quick check, use ctest --test-dir build -L unit -LE slow --output-on-failure.

For UI changes:

cmake --build build
ctest --test-dir build --output-on-failure
tools/e2e/visual_polish_smoke.sh

For simulation, scene model, data conversion, or memory changes:

cmake --build build
ctest --test-dir build --output-on-failure

The suite runs tools/e2e/headless_smoke.py and tools/e2e/roundtrip_smoke.py.

For scene-format changes, also pack/unpack and validate/export the committed scene directories with build/scene_tool. For UI or rendering changes, also run tools/e2e/visual_polish_smoke.sh.

For documentation changes, run python3 tools/docs/check_docs.py; CTest runs it as docs_check in a Git checkout, and its own tests as test_check_docs. The CMake workflow runs it on every pull request. It checks relative links, heading anchors, image references and alt text, images below docs/ that no document uses, documents below docs/ that docs/README.md does not reach through links and the table of contents in docs/index.md, links from a page of the manual, docs/guides/, to a file outside docs/guides/ and docs/images/, the syntax of bash, sh and json examples (a bash or sh example with a here-document is skipped), em dashes and en dashes, absolute local paths, Markdown that only GitHub renders (alerts, <details>, links that start with /, and GitHub links to files in the repository), and the heading order (one # heading first, no skipped levels). It prints one line per finding as path:line: [kind] message and exits with 1 when it finds any. It exits with 2 when it cannot run, for example outside a Git repository. A json example must be valid JSON, so an excerpt with comments or ellipses takes another info word such as text. The script does not fetch external links and does not render Markdown.

Documentation site¶

The site is built from the pages of docs/ with Sphinx, and the C++ reference from the sources in EGTRAIN/QEGTRAIN with Doxygen. Its table of contents is docs/index.md, and its settings are docs/conf.py and docs/Doxyfile. Install Doxygen 1.18 or newer and Graphviz (on macOS brew install doxygen graphviz), then the Python packages in a virtual environment in the build folder with Python 3.12 or newer, and configure again:

python3 -m venv build/docs-venv
build/docs-venv/bin/pip install -r docs/requirements.txt
cmake -S . -B build

On Windows the programs of the environment are in build\docs-venv\Scripts. Then:

cmake --build build --target docs
cmake --build build --target docs-preview

docs builds the reference into build/docs/api/ and the site into build/docs/; open build/docs/index.html. A Sphinx warning fails it. docs-preview serves the pages at http://127.0.0.1:8000 and rebuilds a page when its Markdown changes. It does not rebuild the reference, so run docs first.

A page links to a class with the address of the published reference, such as https://ancientkingg.github.io/EGTRAIN/latest/api/struct_scene_model.html, so the link also works on GitHub. The site build points such a link to the reference next to the page. build/docs-venv/bin/python tools/docs/check_undocumented.py main lists the undocumented classes and members that your branch adds since it forked from main, as the pull request check does.

The same environment builds the manual of the application. When build/docs-venv holds Sphinx at configure time, the build runs Sphinx’s qthelp builder with -t manual on docs/index.md and docs/guides/, then qhelpgenerator, and copies EGTRAIN.qch next to the program, or into Contents/Resources of the macOS app. The configure output says whether it does. Help > EGTRAIN Manual and F1 open the section of the window that has the focus: a window or dock names its section in the property manualSection, and widgets/ManualWindow.cpp maps each section to a page. Without EGTRAIN.qch the application opens that page of the published guides in the web browser. The package jobs build the manual and fail when a package lacks it.
